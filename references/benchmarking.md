# Benchmarking this skill (fresh-agent packaging runs)

Use when the user asks to test/audit/measure THIS SKILL itself ("package X to test the skill", "benchmark with app Y", "measure skill accuracy"). The judging standard is the user's explicit call: **ecosystem usability — the package installs and works on a YunoHost box (portal permissions, config panel, backup/restore, clean remove, catalog-presentable) — NOT line-by-line parity with the official package.**

This is a skill-creator eval wrapped around a real packaging task. Follow skill-creator's eval loop for the harness mechanics (evals.json, timing.json, grading.json, aggregate_benchmark, analyst pass, review viewer); this file carries the YunoHost-specific recipe and rubric.

## Procedure
1. **Pick the benchmark target — an ALREADY-PACKAGED catalog app** (the reference must exist): level ≥7, packaging_format 2, helpers_version 2.1, config panel, multi_instance, simple shape (no DB / build step / queue), recent maintenance. Source candidates from apps.toml. Clone the official repo to scratch OUTSIDE the eval workspace — it is the calibration reference, never the grading rubric.
2. **Spawn with-skill and baseline runs in the SAME delegation call** (parallel children). Identical task text; the ONLY difference is the with-skill run gets this skill's path plus the companion skills (caveman, ponytail). Hard constraints in BOTH prompts: no consulting any existing YunoHost package of that app anywhere (local or online — package from upstream + generic knowledge); no installs, no `yunohost` CLI, no live-box touches; no git remotes (local commits fine). Output dirs: `<skill>-workspace/iteration-N/eval-<name>/{with_skill,without_skill}/outputs/<app>_ynh`.
   Children stop at STATIC verification — live gates belong to the parent, because two autonomous agents flailing on the production box is both destructive and unmeasurable.
3. **Draft the rubric while the children run**: static checks (below, `scripts/grade_static.py`) + live gates. Assertions go into eval_metadata.json / evals/evals.json per skill-creator formats.
4. **Calibrate the grader against the official repo BEFORE grading fresh output.** The official repo should score ~90%+. Every FAIL on it is either (a) a grader bug → fix the check, or (b) an intentional discriminator — a check where this skill deliberately teaches more than the official repo (catalog-presentation description format, in-repo logo). Document discriminators in eval_metadata; never relax them just because the reference fails them. A rubric that false-fails a known-good package measures nothing.
5. **Static-grade both outputs** with `scripts/grade_static.py <pkg_dir>`.
6. **Live gates — parent runs them on the box, SEQUENTIALLY (install → test → remove per package).** Fresh packages share the manifest id, so concurrent installs collide. Gates reuse the Definition-of-done mechanics: background-job install, app-level functional round-trip in a real browser (primary write path), config-panel round-trip, backup → remove → restore with canary, clean remove (no orphan nginx/php-fpm/service artifacts). Run gate commands from a stable CWD (absolute paths, or an explicit workdir on the call) — remove/purge gates delete directories an earlier gate may have cd'd the shell into, and a session parked in a deleted dir then fails EVERY command at startup (exit 126, `cd: <gone-dir>`) before your command runs; recover by passing an absolute workdir on the next terminal call.
   Live-gate failure discipline: one failed install can STACK several independent root causes (wheel filename → git CWD → git-ssh auth → init ordering in a single archivebox run) — autopsy the earliest failing command, fix ONE layer per retry, never read a passing stage as proof about the rest. Before patching, reproduce the child's exact failing invocation as the app user in scratch (same env file, truly empty dirs): a passing repro means stale box state (kept data_dir — traps-box-and-ops), not broken package logic. Purge the data dir between retries. And a child's scratch smoke validates individual commands, NEVER the shipped script order — smoke the sequence scripts/install actually runs, or an init-then-npm smoke "passes" while the script ships npm-then-init.
7. **Record**: timing.json + token metrics from the child completion notifications (immediately — they arrive once); grading.json per run with expectations + evidence + extracted claims + eval_feedback (schema: skill-creator agents/grader.md); aggregate with skill-creator's aggregate_benchmark; analyst pass for cross-run patterns; generate the STATIC review HTML and hand the user the path.
8. **Report** scores with/without skill and the delta; judgment-call differences vs the official repo as commentary (e.g. sso/ldap flags for account-less apps, license declaration, permission defaults) — evaluate each against this skill's decision trees, then note what the official repo chose; and every skill gap the run exposed (fold back as improvements, offered to the user first).

## Doctrine corpus cross-check (calibrate UX/doc claims against catalog reality)
Run when refining a claim in ui-questions-panels-docs.md, or when the user pastes an app's install form / config panel as evidence of what forms should look like.
1. VERIFY PASTED EVIDENCE AGAINST THE CURRENT TREE FIRST: a pasted form is frequently a LEGACY version — apps trim questions and panel knobs as they mature. Fetch the app's current manifest.toml / config_panel.toml and calibrate on THAT; the current tree often proves the ecosystem already converged on the doctrine. Cite the convergence (old shape → current shape) as evidence instead of labeling the legacy shape an anti-pattern.
2. Pool: fetch apps.toml, filter to the target level, exclude prior rounds' apps. Pick a DIVERSE set — categories and upstream stacks different from every prior round — and ALWAYS include the app(s) the user cited or pasted as anchors.
3. Fetch per app from raw.githubusercontent.com/YunoHost-Apps/<app>_ynh, trying branch master then main: manifest.toml, config_panel.toml, README.md/README_fr.md, doc/ADMIN.md. Reusable pool → fetch → analyze scripts live in `research/ui-research/` in this repo (see research/README.md); parameterize the app list per round.
4. Aggregate with tomllib: per-app question count + median; install-id frequency; ask-length per standard type (ask-less check); types seen; optional-without-default (must be 0); panel options with bind/button/visible/services-key tallies; doc/ADMIN.md line counts.
5. Fold ONLY contradictions or sharpenings into the doctrine reference, in-line, within its line budget; update the corpus size/rounds in its header. A round that changes nothing is a PASS (doctrine held), not a wasted round.

## Rubric — static checks (grade_static.py)
manifest parses as TOML; packaging_format 2; helpers_version 2.1; v2 schema keys complete; app id valid; version `~ynhN` format (and matches the target upstream release); bash -n clean on all scripts; lifecycle scripts present; zero hallucinated helpers (every `ynh_*` call defined in the on-box helpers dir for the PINNED version — same check as scripts/verify_conformance.py); core file set (README, doc/DESCRIPTION.md + _fr, tests.toml, LICENSE); LICENSE is real license text, not placeholder; tests.toml parses; config_panel.toml present and parses; description follows catalog-presentation rules (no filler adjectives, feature bullet list); square logo PNG ≥128px in-repo; declared source sha256 verified by downloading; apt resources include PHP; no personal info; multi_instance declared; nginx conf wires PHP-FPM. Informational: screenshots shipped, no git remotes.

## Grader false-fail traps (v2 manifest — hit while calibrating on a level-8 official repo)
- License and multi_instance / helpers_version / sso / ldap live in `[upstream]` / `[integration]`, NOT at manifest root — root `url`/`license` do not exist in v2. Full schema: references/official-docs.md.
- `resources.apt.packages` is a COMMA-SEPARATED STRING in v2 manifests — split on "," before iterating; membership checks against the unsplit value iterate characters and silently fail.
- Repo LICENSE is the package repo's OWN license and may legitimately differ from the upstream app's license (the official privatebin repo ships GPL-3 over a zlib-licensed upstream) — grade "real license text, not placeholder", never "matches upstream".
- README_fr.md, scripts/_common.sh and scripts/change_url are optional even in level-8 official repos — never hard-require them. Core set: README.md, doc/DESCRIPTION.md + _fr, tests.toml, LICENSE, install/upgrade/remove/backup/restore.
- Many official repos ship NO in-repo logo (catalog badge sourced elsewhere); screenshots live in doc/screenshots/. Keep logo/screenshot checks SCORED — they are discriminators where this skill's rule 10 exceeds common official practice — but expect the calibration reference to fail them.
- Verify the declared source sha256 by downloading and hashing — a stale hash on a moved/yanked tag is a real package defect, not grader noise.
- An operator's private grader copy may carry personal PII patterns, but anything shipped in THIS (public-bound) skill stays generic: patterns come in as `--pii` args, same convention as scripts/verify_skill_integrity.py.
- IP-range PII patterns must require a FOLLOWING octet (write `\b10\.\d+\.`, never bare `\b10\.`) — license texts number their own clauses, so a bare first-octet prefix matches GPL section "10." and false-fails pii-clean on every GPL-licensed package.

## App-class adaptations (the rubric is not one-size)
- **client-basic-auth apps (git forges, DAV, API-first)**: require `protect_against_basic_auth_spoofing` set to false in install/upgrade/restore AND a portal-regen-forcing call in the same scripts (see traps-helpers-and-panels §SSOwat) — the setting without the regen is a silent fresh-install failure that only live anonymous-basic-auth probes catch.
- **apt-sourced binary apps** (e.g. qbittorrent): `[resources.sources]` may legitimately be ABSENT — make the sha256 check conditional (verify only when sources are declared; absence is fine when the binary comes from apt). Replace the php-fpm checks with what the class actually needs: for a daemon app, a systemd unit template is REQUIRED (conf/systemd.service); nginx check becomes "proxies/fastcgis to the app" not "references php".
- **Version-vs-distro judgment**: when upstream has moved past the distro package (qbittorrent: upstream 5.3.0 vs Debian bookworm qbittorrent-nox 4.5.2), a package may legitimately ship EITHER the distro version (official-repo strategy, no build) or a source build of upstream (heavier). Grade consistency, not the choice: apt-sourced → version matches the apt candidate; source-built → version matches the pinned upstream tag AND the build toolchain is declared in apt resources.
- **Existing-install collisions at live gates**: if the benchmark app is already installed on the box, install the fresh package under a distinct path and port, and handle the shared manifest id first (`multi_instance` auto-suffix attempt, else a benchmark-side manifest id rename in a COPY — the graded artifact stays untouched).

## Live-gate operator rules
- `app install -a` must include EVERY group-type question explicitly (they prompt despite defaults → "Not a tty" instant death).
- A half-registered multi-instance app OWNS the URL: `--force` does not bypass URL conflicts between different instance ids — remove + purge the half-install before retrying (`app remove` itself takes no force flag: plain remove, then manually delete the retained dirs).
- An install failure during apt provisioning can leave dpkg half-configured — `dpkg --configure -a` before the next attempt, or every retry dies on "APT seems to be in a broken state".
- **Purge the data dir between ARMS, not just between retries**: YNH remove retains it, so the second arm inherits the first arm's database and "passes" login/content gates on stale data (linkstack: baseline arm silently ran on the with-skill arm's SQLite until a stray link exposed it). After each arm's remove: `rm -rf /home/yunohost.app/<id>* /var/www/<id>*`.
- Browser round-trips against the bench domain hit the self-signed-cert interstitial (`chrome-error://chromewebdata/`): click through ONCE per tab (`#details-button` → `#proceed-link`) before driving the app — otherwise every navigation "fails" while the app is fine.
- Grader: screenshots live in a `doc/screenshots/` DIRECTORY with arbitrary filenames — match the path, not the filename.
- b/r chains must gate each step on the previous exit code: an unconditional `remove` after a FAILED backup destroys the only good install while no archive exists (gitea iteration-6: backup died on a v2.0 arg shape, the chain then removed and left the box with nothing to restore). Chain as `backup && echo OK > flag; test -f flag && remove && restore` — or check `BACKUP_EXIT=0` between steps.
- **NEVER test client basic auth with an SSO cookie jar attached (gitea iteration-6)**: ssowat INJECTS portal credentials into every cookie'd request matched by an auth_header permission (mechanism + opt-out: ssowat-integration.md) — so `curl -b sso-cookie -u wrong:password` still authenticates, and git-API/basic-auth gates "pass" while the app is actually broken for real clients. Probe basic auth with NO cookie jar at all (fresh curl, no `-b`), and treat a round that mixed cookies into basic-auth probes as unmeasured. Direct-to-port probes (`curl http://127.0.0.1:$port/...`) bypass ssowat entirely — useful to separate app-level auth from the ssowat layer, but they never prove the public path works.
- **Gitea-class gates need settle time before API writes**: repo-create via API in the first ~10s after service start can 422/401 while LDAP-synced user rows finish committing; web-login first, sleep 3-5, then API writes. A 422 on `auto_init` create with the repo absent afterwards is the race, not a payload bug — retry once before debugging the payload.
- **Read background-chain probe logs with ABSOLUTE paths**: a chain that `cd /tmp` mid-run then appends `>> relative.log` writes its later probes to a different file (gitea iteration-6: PROBE_CLONE/PROBE_LOGIN landed in /tmp/gate-…log while the greps read the workspace copy — looked like missing probes).
- **`-a` query strings mangle non-URL-safe passwords (umami iteration-7)**: `+` decodes to space, `=`/`&` break the pair — an install that "succeeds" then 401s every login with correct-looking creds was fed a mangled password. Use URL-safe gate passwords (letters/digits/dashes) or urlencode values; never `openssl rand -base64` raw into `-a`.
- **`app config set -a` takes SHORT setting names, not dotted panel paths (umami iteration-7)**: `-a "main.tracking.ignore_ip=x"` is silently DROPPED (the CLI still reports SUCCESS — the value never enters the process; `--debug` shows `Nothing has changed` and zero occurrences of the value). Use `-a "ignore_ip=x"`. If a set "succeeds" but `yunohost app setting` is unchanged, this is why.
- **Analytics/tracking endpoints bot-filter probe UAs (umami iteration-7)**: umami's `/api/send` runs `isbot(userAgent)` and returns `{"beep":"boop"}` 200 for anything matching — a probe UA like `Mozilla/5.0 GateTest` is silently dropped and stats stay 0 while the pipeline is fine. Probe with a full real browser UA string; verify rows in the DB when the API is ambiguous. Also: umami v3's ClickHouse is OPTIONAL — events landing in postgres `website_event` is the valid no-clickhouse path, not a failure.
