# Lifecycle traps: install/upgrade/backup/restore/remove durability (ynh-app-packaging)

Carved from platform-traps.md 2026-10-27 (router there). What sticks, what reverts, what restore really executes.

## Editing an existing package safely (lessons from live upgrades):
- Text-replacing script regions can partially match and leave ORPHAN lines (an old `[ -n "$var" ] || ynh_die` surviving under a new helper call broke the first plausible production upgrade). After any multi-line replace: grep for variables the deleted code owned, `bash -n` every touched script, and test with a real `yunohost app upgrade <app> -u <local-repo-clone>` when installed (it safety-restores on failure). Prefix `unset PYTHONPATH` or the pre-upgrade safety backup dies on pydantic.
- Before deleting a 'dead' file, grep the tree for consumers of what it PRODUCES: opengym's 'unused' sso-map.conf template defined nginx var `$opengym_auth` that conf/nginx.conf referenced — deleting the template without the nginx hook breaks every future nginx provisioning. Removing a tool means removing its hooks too (map block in install/upgrade/restore, cleanup in remove, the nginx proxy_set_header, README bullets).
- Check `yunohost app list` before promising a live upgrade test: the admin uninstalls apps without notice — upgrading a missing app exits harmlessly but validates nothing.

## Upgrade-durability doctrine (verified against /usr/share/yunohost/helpers.v2.1.d on the box, 2026-10-26)
THE FACTS that decide what sticks:
- `ynh_setup_source` has NO version gate — it re-extracts the source on EVERY script that calls it (install/upgrade/restore, even same-version). Everything under `--dest_dir` is wiped except the `--keep="f1 f2"` list. Any hand-edit or sed under $install_dir is gone on the next upgrade pass.
- Config-panel applies and `change_url` re-render templates from the ARCHIVED tree (`/etc/yunohost/apps/<app>/conf/`), so repo fixes only take effect after `yunohost app upgrade -u <clone>` refreshes the archive.
- settings.yml survives upgrades (secrets, custom keys); it is WIPED on remove (secrets regenerate). Portal permission groups / logo pins live in settings too: survive upgrade, lost on reinstall.

THE RULES:
1. NO LIVE-ONLY FIXES. A fix made directly on the box (app source, rendered /etc config, nginx conf, unit file, helper bin) is UNPROVISIONED until it exists in the repo AND has been landed by a real `yunohost app upgrade -u <clone>`. Same session, same commit — otherwise the next upgrade or restore silently reverts it and the fix is indistinguishable from "never worked".
2. Every fix goes into its durable home: app-code patch → fork upstream + pin fork tarball in `[resources.sources]` (or upstream PR), NEVER sed on installed files; config fix → conf/ template; runtime env fix → env template re-rendered from settings; new runtime file (helper, sudoers, ACL, log dir, browsers dir) → provisioned by a shared `_common.sh` function called from install AND upgrade AND restore; live-state repair (db row, chown, re-pin) → idempotent repair function on the same three paths. The upgrade script must be a strict superset of install's provisioning steps — "it worked at install time" provisions nothing for the next version.
3. `--keep` is the ONLY sanctioned mutable file set inside $install_dir (app-written sqlite, secrets the app mints itself). Data belongs in $data_dir instead whenever the app lets you point it there — $data_dir is backed up; $install_dir is disposable by design.
4. THREE-PATH CONVERGENCE GATE, before reporting any package/change done: (a) same-version `yunohost app upgrade -u <clone>` TWICE in a row — this is what catches scripts that only pass on fresh installs (missing mkdir/chown/re-render is invisible to install); (b) after the double upgrade, re-run the basic-functionality gate (references/quality-gates.md §0a), not just rc=0; (c) backup → remove → restore round-trip, because restore executes the ARCHIVED scripts against a re-created $install_dir — the one path that proves the durability claims.
5. State what does NOT survive in doc/ADMIN.md for every non-package-owned mutable thing (permission group edits, logo pins, user hand-edits to app configs that the package manages): the admin must be able to reinstall without losing their setup by following the doc alone.

## Native source patches: patches/<source_id>/*.patch (built-in durability for app-code fixes)
- HOW IT WORKS (verified in helpers.v2.1.d/sources + app.py, 2026-10-26): after extracting + in_subdir-stripping the tarball into $dest_dir, ynh_setup_source checks $YNH_APP_BASEDIR/patches/$source_id/ and applies every *.patch with `patch --strip=1` from inside $dest_dir. Repo-root `patches/main/` covers the default source id.
- WHERE IT RUNS: install and upgrade-from-package (YNH_APP_BASEDIR = the freshly extracted repo, full tree incl. patches/). It does NOT exist in the registered app dir — APP_FILES_TO_COPY (app.py) copies only manifest, config_panel.toml, scripts, conf, hooks, doc into /etc/yunohost/apps/<app>/ — so backup/restore archives carry no patches/ either. NOT harmless if the restore script re-extracts sources: on restore YNH_APP_BASEDIR = the backup's staged settings dir, patches/ is absent, and the sources come back UNPATCHED while the restore still reports Success (loomio dogfood 2026-10-27: hocuspocus port + npm-engine patches lost; only grep of the extracted tree caught it).
- DURABILITY FIX (verified green, loomio_ynh backup→remove→restore): in install AND upgrade, right after ynh_setup_source, run `cp -a "$YNH_APP_BASEDIR/patches" "/etc/yunohost/apps/$app/patches"` — settings/ is what backups archive, so restore stages patches/ as part of YNH_APP_BASEDIR and setup_source applies them normally. 2 KB, no re-download. The alternative (calibreweb_ynh pattern) is `ynh_backup "$install_dir"` of the whole patched tree — correct but heavy for build-stack apps (vendor/bundle + node_modules).
- NEVER call `patch` manually from lifecycle scripts: the call is redundant (the resource already applies patches/<source_id>/ on every extract) and resolves its input path against the staged work dir, which on restore has NO patches/ tree — `patch: **** Can't open patch file` mid-restore. All source patches route through the resource; scripts/ should contain no `patch -p1` at all.
- FAILURE BEHAVIOR: inside package_check/CI a failing patch ynh_die's the run; on a live server it only warns ('Warn your packagers /!\ Patch ... failed to apply') and CONTINUES with an unpatched tree — a drifted patch is silent in production. The double-upgrade gate + CI are what catch it.
- UPSTREAM-BUMP PROCEDURE: extract the new tarball to scratch, re-derive each diff, `patch -p1 --dry-run` against the new tree, commit regenerated patches + new sha256 together. Patches drift exactly like conf templates — same review discipline.
- PREFER patches/ over forking for small, stable fixes (header tweaks, path hardcodes); fork only for real divergence. Same as everything else: NEVER sed installed files.

## Backups and restore mechanics
- RESTORE PRECONDITIONS (admin docs, verified 2026-10-27): the app must NOT already be installed when restore runs (old version → uninstall first), and its domain must already exist on the box; app IDs collide on server merges (nextcloud vs nextcloud__2). Write scripts/restore to provision from settings + backup dir ONLY — never assume anything about a pre-existing install.
- `ynh_restore` SAFEGUARDS existing destinations: an existing file/dir at the target is moved to /var/cache/yunohost/appconfbackup/ when lighter than 500MB, otherwise REMOVED — restore does not merge, it displaces.
- `ynh_restore "/etc/php/$v/fpm/pool.d/$app.conf"` does NOT reload php-fpm: the pool socket is only (re)created when the master re-reads its pools, so every PHP route 502s after restore until fpm is poked (castopod 2026-10-28 — gate caught it as post-restore 502 with static assets still 200). End the system-config phase with `systemctl reload "php$php_version-fpm"` (or `ynh_config_add_phpfpm`) after restoring the pool conf. Same class: any service whose conf file is ynh_restore'd (nginx gets reloaded by YNH's own restore flow; fpm does NOT).
- Core-only backups exist beyond the upgrade safety pass: admins can set `do_not_backup_data=1` permanently (`yunohost app setting <app> do_not_backup_data -v 1`); `ynh_backup` then skips $data_dir and /var/log/$app, and data-heavy apps' upgrades auto-use core-only. scripts/backup must cleanly separate core from bulk data so a core-only restore still reinstalls (the model is "reinstall + reincorporate data" — venvs/node_modules/apt deps are never in the archive by design).
- The only user-side exclusion lever is an empty `.nobackup` file, and it only works for FIRST-LEVEL subfolders of /home — don't count on it for anything under $data_dir.
- On FRESH install the install_dir folder is DELETED if it already exists (admin docs, verified) — pre-existing /var/www/$app content does not survive install; don't design around it.
- UNDECLARED permissions are DELETED on upgrade: every permission the manifest/resources ever created must stay declared in every subsequent version, or users' access groups vanish silently on the next upgrade.
- Debian migrations rebuild Python apps' venvs (driven by a `*.requirements_backup_for_bullseye_upgrade.txt` marker beside the venv — admins may delete it to opt out) and jump PostgreSQL 13→15; users repair broken apps with `yunohost app upgrade -F` (same-version forced rerun) — upgrade scripts must be idempotent under a forced same-version run.
- Backups run the ARCHIVED scripts: `yunohost backup create` copies scripts from `/etc/yunohost/apps/<app>/scripts`. Restore executes the archived copy — workspace fixes do nothing until you reinstall (refreshes registry) then re-create the backup. Restore must also re-render env files from settings (app removal regenerates `db_pwd`), not restore the archived env verbatim.
- `ynh_backup` (helpers 2.1) has NO exclusion option — it backs up whole paths only. A wholesale `$install_dir` backup drags build caches along (linkding: .cache 84M + node_modules 27M inside a 499M archive; the pinned runtime+venv are deliberate for offline restore). Either accept and STATE the archive size in doc/ADMIN.md, or declare subpaths individually (brittle: upstream tree changes silently escape the backup).
- Corollary of the setup_source wipe: SYMLINKS under $install_dir (e.g. a `data -> $data_dir` shim) are destroyed by every `--full_replace` pass unless listed in `--keep`. Any symlink-recreation step must run after EVERY `ynh_setup_source` call (put it in the shared deploy superset). And `ln -sfn` cannot replace a REAL directory that the tarball re-created — if upstream ships the dir, the ln silently fails and the app writes into $install_dir: a data split that surfaces only as "database has no bookmarks after upgrade".
- Upgrade safety backups run with `BACKUP_CORE_ONLY=1`: the pre-upgrade auto-archive EXCLUDES `$data_dir` by design ("will not be saved, because BACKUP_CORE_ONLY is set"). Data survival across a failed upgrade rests on remove-never-purging + $data_dir staying in place, NOT on the safety backup — do not promise users the safety archive contains their data.
- Postgres data is NOT auto-dumped by the v2.1 resource: the resource provisions/drops role+db only. `scripts/backup` must dump (`ynh_psql_dump_db > db.sql` — lands in the archive's apps/<app>/backup/), and `scripts/restore` must create any superuser-only extensions FIRST (as postgres, before the dump's CREATE EXTENSION lines run as the app role), then load with `ynh_psql_db_shell < ./db.sql` from the staged backup dir. Verified round-trip: rows + panel settings + quoted env all survive backup→remove→restore.
- Restore data-integrity check must compare against WHAT WAS BACKED UP, not against pre-cycle state: a remove→fresh-install→backup→restore chain restores a legitimately empty db. Create a canary row + change a panel setting right before the backup, then assert both after restore.
- doc/POST_UPGRADE.md content is printed by the core at the end of a CLI upgrade — write user-meaningful "what survives / what to do" lines there, it's free UX.
- data_dir is deprovisioned on remove only with the purge option (YNH 12 remove asks).

## Remove cleanliness
- conf_regen hooks: delete their regenconf-TRACKED files BEFORE the final `regen-conf` — regenconf only forgets a hash when the file is absent from disk AND pending, otherwise a later restore refuses to recreate the maps.
- Half-registered app cleanup (install died before its unit existed): `yunohost app remove` has no force flag and the remove script aborts on the missing unit. Plant a minimal valid placeholder at `/etc/systemd/system/<app>.service` (`[Unit]` + `[Service] Type=oneshot ExecStart=/bin/true` + `[Install]`), `systemctl daemon-reload`, remove the app, `apt-get purge -y` leftover app debs, then delete the placeholder.
- remove runs WITHOUT `set -eu` (every other lifecycle script runs with it) — a cleanup line failing mid-remove doesn't abort it.
