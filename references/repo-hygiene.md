## Full-repo example_ynh conformance audit + screenshot/logo sweep (fleet-wide, all *_ynh repos)
- Audit script per repo: bundled `scripts/verify_conformance.py <repo-dir>...` covers banner bytes/heads/modes/file-set + bash -n (rc≠0 lists every issue; helper-hallucination diff, PNG/logo validity, PII sweep and package_linter stay manual). Then `git ls-files` vs the example_ynh required-file list; PNG validity from raw IHDR bytes (size, square) + IDAT corner alpha; script modes from `git ls-files -s`. Typical findings: missing fr docs / PRE_/POST_ upgrade-install docs, missing .gitignore (4 repos), change_url/config/_common.sh shipped 755, logo 128px or entirely absent, screenshots directory holding only a README stub.
- Script-banner conformance (2026-10-16 wave, ground truth = live example_ynh clone): banner line is `#` + 49 `=` (50 chars) exactly, titles ALL CAPS ASCII. Canonical heads — install/remove/upgrade/change_url: shebang, blank, IMPORT GENERIC HELPERS banner, blank, `source _common.sh`, `source /usr/share/yunohost/helpers`. backup/restore: same but `source ../settings/scripts/_common.sh` preceded by the literal comment `# Keep this path for calling _common.sh inside the execution's context of backup and restore scripts`. config: IMPORT banner + helpers source, NO END OF SCRIPT banner; `source _common.sh` is allowed when the apply path needs shared logic (official catalog precedent: grav/nextcloud/my_webapp source it in config — do not flag repos for this; only the ../settings/ path is wrong there); a repo with no scripts/config is conformant — upstream marks it optional. END OF SCRIPT banner sits above the final progression/info line of the six lifecycle scripts. GAP banner-insert transforms miss: scripts that ALREADY had the `../settings` source lack the Keep-comment (pair-insertion only fires when the source is absent) — grep backup/restore for the comment separately. Verify helper names by diffing every `ynh_[a-z0-9_]+` in scripts against `YNH_HELPERS_VERSION=2.1 bash -c 'source /usr/share/yunohost/helpers; declare -F'` (148 fns) — catches hallucinated helpers a banner pass never looks at. When double-checking a parallel agent editing the same clones: snapshot read-only until its tree goes clean (dirty=0), then land your own fixes as pure insertions; its state churns minute-to-minute, so re-run verification immediately before reporting.
- Ports-in-diagnosis chain (verified on YNH 12.1 source): manifest `[resources.ports]` `exposed = "TCP"/"UDP"/"Both"` only opens the YunoFirewall port (+UPnP router forward if `upnp=true`); the ports DIAGNOSIS reads `needs_exposed_ports` from /etc/yunohost/services.yml, set ONLY by `yunohost service add <svc> --needs_exposed_ports <port>` (template documents the flag; re-calling service add in upgrade refreshes flags on old installs). Remote probe is diagnosis.yunohost.org/check-ports, TCP-connect only — UDP-only ports permanently red-flag even when correctly forwarded. USER DIRECTIVE: include UDP-only ports in needs_exposed_ports anyway, as constant forward-reminders — the admin picked permanent red over silence; state that tradeoff once in the report, never silently exclude them. Apps appear in `yunohost service status` and the services/ports diagnosis only if the package calls service add — packages that skip it are invisible to both subsystems entirely. oneshot/docker-compose units report status 'unknown' — pass `--test_status="docker ps --format '{{.Names}}' | grep -qx $app"`. Live shortcut without app upgrade: run the same `yunohost service add` on the box directly. Ports resource key is `exposed` — `exposure = "none"` is silently ignored (shipped in archiveteam-warrior).
- Logo sourcing ladder that actually worked: in-repo brand SVG from the UPSTREAM CODE repo is best (freenet: an official logo SVG sits under the core server's commands/assets tree in freenet-core; anubis: `docs/static/img/logo.svg` in TecharoHQ/anubis — verify byte-identical to what you render). Find it via `gh api repos/<up>/git/trees/HEAD?recursive=1 --jq '.tree[].path' | grep -iE 'logo|icon|svg'`. PWA sites ship icon-512.png. Dashboard apps: `dashboard/public/logo-*.png` in upstream repo. Nothing found → author an original SVG (flat vector glyph, no <text>) and `rsvg-convert -w 512 -h 512 in.svg -o out.png`. GitHub raw of guessed brand URLs 404s ~always — go through the repo tree listing instead.
- Live screenshots of SSO-gated apps: create throwaway user (`yunohost user create ci_user -F ... -d domain -p "$RANDOMPW"` — password via env var, never in transcript), add to needed group (`yunohost user group add admins ci_user`), then run `yunohost app ssowatconf` (see trap below), log in through the portal FORM in the browser tool, visit each app, capture. Cap's dashboard gate asks the instance admin key AFTER portal login — the key-entry screen is an acceptable dashboard screenshot; do NOT type the admin key into the browser. Static-site apps not installed anywhere: `python3 -m http.server` the package's sources/www into the browser for a true-to-package shot. Pure-redirect quicklink packages: screenshot the redirect destination. CLI-only apps (ooni-probe): legitimately no screenshots — document in doc/ADMIN.md instead.
- TRAP: YN12 group-membership changes do NOT regenerate /etc/ssowat/conf.json — its per-permission `users:` list stays stale and every visit 302s to `sso?msg=access_denied` despite correct `getent group` output. Fix: `yunohost app ssowatconf` (writes conf.json; there is NO `regen-conf ssowat` category on this box). Also: an ssowat JWT copied out of Set-Cookie and re-set via document.cookie is rejected — use the real form login.
- TRAP: agent shells may inject PYTHONPATH pointing at a venv NEWER than the system python3 (Hermes: python3.14 venv vs 3.11 system) — every `yunohost ...` CLI call then dies on `ModuleNotFoundError: pydantic_core._pydantic_core` (cp314 wheel vs cp311 interpreter), and package_linter dies on `rpds.rpds`. Commands look like a broken server; they are not. ALWAYS `unset PYTHONPATH` before yunohost CLI commands; for package_linter use the agent runtime's own venv python (Hermes: `/root/.hermes/installs/*/venv/bin/python3`).
- package_linter: clone YunoHost/package_linter, pip install -r requirements.txt, expect rc=1 + exit 'not in YunoHost's application catalog' for all personal repos — that is the ONLY tolerated failure; grep the output for any other ✘/⚠ line. Issues print as INDENTED ` ! ` / ` ✘✘✘ ` lines, never line-initial `[` — eyeball raw output once before trusting any grep filter; a pattern that matches nothing renders a false PASS across every repo.
- After pushing logo changes for INSTALLED apps, re-pin the portal tile: `yunohost user permission update <app>.main --logo logos/<app>.png`, verify logo_hash in settings.yml == sha256 of the file and /etc/yunohost/portal/<domain>.json carries the new hash; hard-refresh note for the user.

## NOTHING-leaks rule (ABSOLUTE — required scrub+audit before EVERY push to a *_ynh repo)
No file, image, or commit may ever enter the repository if it reveals the user's personal information or server setup: real names, emails, personal domains (including in manifests' `upstream.website`, doc examples, scripts' default args, READMEs), portal usernames/groups, public/private IPs, hostname lists or subdomain inventories (they map the whole stack!), app data captured from production (scrape job names, watched lists, comment content, analytics sites), absolute paths that name users. This applies to HISTORY, not just HEAD.
MANDATORY pre-push audit (agent or script, all three layers):
1. TEXT, current tree: build the personal-information pattern list once (real name, every personal domain, portal usernames, public IP) and in every repo `grep -riE '<pi-patterns>' --exclude-dir=.git`, plus `grep -riE 'nohost' | grep -viE 'yunohost'` (the word YunoHost contains 'nohost' — filter it; `YunoHost/apps_tools` README comments are safe). Also grep for the user's own subdomain names — the subdomain inventory itself is the leak.
2. TEXT, full history: `git log --all -p | grep -icE '<same patterns>'` per repo — must be 0. If >0: git filter-repo the offending path(s), force-push to the DEFAULT branch (check `gh api repos/<r> --jq .default_branch` first — some repos default to `master`!), delete stray branches, verify no remote commit still references it via commits API.
3. IMAGES: vision-sweep every screenshot AND logo (montage batches): ask explicitly for names, domains, usernames, emails, site/app data belonging to the user. A single visible personal-domain row in a UI table = reject the capture, re-shoot through the sanitized proxy or use official upstream assets.
Personal-upstream exception: when an app IS the user's own project, the personal domain is exactly what the rule forbids — linter says `website` must not be a code repo, so DROP the `website` key entirely and keep only `code`.
Before calling a package 'catalog ready': the 3-layer audit passes, `doc/screenshots` are real embedded images from official/sanitized sources, `logos/<id>.png` 512px square transparent PNG and referenced in README <h1>, README_fr + doc/ set complete, no linter failures except 'not in catalog', and no build junk committed (`.manifest.v2.schema.json`, `.tests.v1.schema.json`, `.spdx_licenses`, `.config_panel.v1.schema.json` are linter-run artifacts — untrack them, ignore them; example_ynh's own .gitignore does NOT list them, it is minimal `*~/*.sw[op]/.DS_Store` — artifact ignores are our/linter additions, harmless but not template).
- DOTFILES ARE CANONICAL (verified against upstream 2026-10-15): example_ynh SHIPS `.editorconfig`, `.gitattributes`, `.github/ISSUE_TEMPLATE.md`, `.github/PULL_REQUEST_TEMPLATE.md`. They are part of the template a reviewer expects — NEVER delete them as 'unreferenced scaffold junk' in a verbosity/ponytail pass; example_ynh conformance outranks the unreferenced-file heuristic. (Deleting them in 3 repos and then restoring cost a round-trip.) A scaffold that shipped only `.github/workflows/linter.yml` is INCOMPLETE, not over-shipped: copy the missing ISSUE/PULL_REQUEST templates from example_ynh. These repos deliberately ship NO CI workflows (keep that one removed).
- tests.toml review-complexity gate: a catalog reviewer's first verification question is 'does upgrade work?' — declare real `test_upgrade_from.<sha>.name = "<version>"` entries from the repo's OWN history so package_check exercises upgrades. Generator that worked: walk `git log --format=%H -- manifest.toml` newest→oldest, map each commit to its manifest version, and for each previous version (≠ current) take the LAST commit where that version was still in effect (walk parents while the version string stays identical — that state has all its fixes), abbreviated 7-char sha as the id, max ~3 entries (openshorts: ynh5/6/7; plausible: ynh1/2/3). Single-version repos (7 of 15) have nothing to declare — ship the clean minimal file (`#:schema` header, `test_format = 1.0`, bare `[default]`), NOT the 2.8KB commented template scaffold (commented-out entries are noise a reviewer must skim to discover are inert). Required install questions with NO default and NOT optional (cap's admin_key) must get a `args.<key> = "ci-..."` line under `[default]` or CI cannot even install.

## Screenshots / logos / docs: sourcing + privacy rules (user directive 2026-10-15, reinforced twice)
- SOURCE PREFERENCE: screenshots, logos and doc images must come from the SOURCE APP's own repo or website whenever it ships them — official first, live capture second. Working sources found: upstream repo trees (`gh api repos/<up>/git/trees/HEAD?recursive=1` — Watcharr ships screenshot/*.png at repo root, umputun/remark42 has screenshots/comments.png), product sites' /docs (plausible.io/docs/img/plausible-analytics.png), PWA icon-512.png, upstream dashboard/public/logo-*.png. NO third-party/blog screenshots.
- HARD PRIVACY GATE: no screenshot may ever contain the user's real name, personal domains, or personal usernames. Live captures of admin UIs that list the server's REAL domains (anubis GUI shows `yunohost domain list`!) are LEAKS — vision-verify every screenshot (montage batches, ask for names/domains/usernames/emails explicitly; 'YunoHost' contains 'nohost' — exclude that word) before shipping.
- Sanitized capture pattern (verified on anubis): read-only stdlib http.server proxy on a scratch port forwarding to the app's loopback port, inject `Ynh-User: admin` header (server-side gate reads it; no login typed anywhere), and byte-replace the response body: personal domains→example.com, name fragments→example, real usernames→admin. Screenshot through it. Kills the process after; zero production changes.
- PII SHIPPED BY MISTAKE → scrub history, don't just delete: `git filter-repo --invert-paths --path doc/screenshots/<file> --force` (single-file pip script at /usr/local/bin/git-filter-repo; PEP668 blocks pip). For TEXT leaks inside kept files use `--replace-text <file>` with `regex:`-prefixed lines ('foo\.com==>bar' WITHOUT the prefix is FULL-STRING-match and silently replaces nothing). filter-repo DROPS the origin remote every run (re-add) and RESETS tracked files to the rewritten HEAD (any uncommitted README fixes get clobbered — commit fixes BEFORE filtering). Force-push, then re-verify via `gh api .../commits` that no commit touches the scrubbed path. Leaks hide in manifest `upstream.website`, source-file default args and SHIPPED DEMO CONTENT (a shipped template footer once carried a personal domain + personal photos); `git log --all -p | grep -ic` is the only honest check.
- BRANCH PITFALL (cost a PII purge once): repos can mix default branches — some default to `master`, the rest `main`. `git push HEAD:main` on a master-default repo creates a SECOND branch and leaves the old history (incl. PII) as the visible default. ALWAYS `gh api repos/<r> --jq .default_branch` before force-pushing rewrites; delete stray branches after.
- A broken <img> path in a README IS a missing logo to the user: after any README edit, resolve every reference — local paths against `git ls-files`, external URLs against HTTP status (raw.githubusercontent CDN caches ~5 min; verify rewrites via `gh api contents`, not curl). YunoHost/apps catalog logo URLs 404 for non-catalog apps — use the repo-local logos/<id>.png in the <h1>. Watch readme-generator output with `rgb(...)` badge colors: parens break markdown URLs, percent-encode.

## Dashboard tile logo (non-catalog apps) — verified procedure
A freshly installed app shows the generic YunoHost tile until a logo is pinned; the tile icon is NOT set by `logos/<app>.png` in the package (that only serves the catalog listing). To pin it:
1. Ship `logos/<app>.png` in the package (square PNG ≥180px; author an original SVG if the upstream icon is unusable — `rsvg-convert -w 512 -h 512 in.svg -o out.png`; check legibility at 96px, render vector glyph paths instead of `<text>` since rsvg's font pick may fall back to serif). The pin validates the PNG magic header (89 50 4E 47 0D 0A 1A 0A) and rejects anything else with "Only PNG logos are supported" — upstream .webp/.svg/.ico icons MUST be rendered to PNG first, preserving the alpha channel. For "make sure it's transparent" requests, verify corner-pixel alpha == 0 by decoding the IDAT chunks (walk PNG chunks, zlib.decompress, un-filter scanlines) — `file` saying 'RGBA' proves the channel exists, not that corners are transparent, and PIL may not be installed.
2. Pin on the box: `yunohost user permission update <app>.main --logo /path/logo.png` — copies to `/usr/share/yunohost/applogos/<sha256-of-file>.png` and writes `logo_hash` into `_permissions.main` in `/etc/yunohost/apps/<app>/settings.yml`.
3. Verify (the `yunohost user permission list` output does NOT show it): check `logo_hash` in settings.yml AND that the per-portal app list carries it: `/etc/yunohost/portal/<main_domain>.json` → `apps['<app>.main'].logo` = `/yunohost/sso/applogos/<hash>.png`; then curl that URL (expect 200 image/png). ssowat's `conf.json` `permissions` block never contains logos — don't chase it there. The portal caches applogos aggressively: after re-pinning, a still-blank tile in the user's browser is usually cache — have them hard-refresh (Ctrl-Shift-R) before re-debugging the pin.
4. logo_hash survives app upgrade but is lost on remove+reinstall — re-pin after reinstalls (or a catalog PR makes it permanent via catalog logo_hash). The webui's own /static logo and the portal tile are SEPARATE surfaces: serving /static/<app>.png 200 verifies only the former. When a reinstall is requested "so a logo change takes effect", the permission-update re-pin is the step that makes it take effect on the tile.
5. Reinstall wave procedure (verified 2026-10-11, 10 apps): `yunohost backup create --apps <a>` → remove → install from the GitHub clone (`/tmp/y_install.sh` pattern: `yunohost app install . --args ... --force` bg job; --force skips DANGER prompt) → restore DATA selectively from the backup tar (tar paths: `apps/<app>/backup/home/yunohost.app/<app>/`, PG dump `db.sql`, ClickHouse dumps `clickhouse/*.native`). Permission groups (visitors on public mains) and logo pins must be RE-APPLIED after every reinstall — they live in settings, not the package. PG dump restore: `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` then `psql -f db.sql`, then `ALTER SCHEMA public OWNER TO <app>; GRANT ALL ON SCHEMA public TO <app>;` (skipping the owner fix = ecto migration 'no schema has been selected' + app crash loop 'relation salts does not exist' because schema_migrations can't be written), then run migrations (`bin/<app> eval <Module>.Release.interweave_migrate` inside `sudo -u <app> bash -c 'set -a; source <env>; set +a; ...'`). ClickHouse: auth via the password in `/etc/clickhouse-server/users.d/<app>-default-password.xml` (app setting `ch_password` can be EMPTY on reinstall), re-run dictionary migrations BEFORE inserting events_v2/sessions_v2 (dictGet baked-password 516). Domainless apps (ooni-probe) can NEVER show a portal tile: `--show_tile True` is refused without a URL — don't chase it.
6. Quicklink tiles for external services: minimal package = manifest (domain+path+init_main_permission, `[resources]` with system_user/install_dir/permissions main.url="/"), conf/nginx.conf with BOTH `location = __PATH__ { return 302 https://target/; }` AND `location __PATH__/ {...}` (exact-match for the no-slash URL the portal tile links to), stub lifecycle scripts, tests.toml, LICENSE, README, doc/DESCRIPTION.md, logos/. TRAP: without `helpers_version = "2.1"` in [integration] the OLD helpers load and `ynh_config_add_nginx` = command not found → install fails. Create the GitHub repo via API first (`POST /user/repos`), then push. Pin logo with `yunohost user permission update <app>.main --logo`.
7. Logo sourcing fallbacks (best first): official site /press page → brand GitHub repo → favicon (last resort, must upscale with `convert -resize 512x512`, quality poor for detailed marks) → seeklogo/brandslogo CDN via a proxied URL the user supplies (600x600 seeklogo PNGs are clean). NEVER leave a placeholder text tile when a 404 fallback exists.

## Linter + example_ynh conformance sweep (fleet-wide *_ynh repos)
- package_linter greps raw file TEXT: the words `add_header`/`more_set_headers` inside COMMENTS trip the nginx checks — never name the directive in a comment. more_set_headers must match `more_set_headers +["'][\\w-]+\\s?: .*["'];`.
- nginx conf referencing a runtime-defined variable (map written by a contrib/glue script) breaks ALL nginx on fresh install: `unknown "var" variable` aborts the reload inside ynh_config_add_nginx. Ship a default identity map (`map $http_authorization $var { default $http_authorization; }`) in conf/, deploy BEFORE ynh_config_add_nginx (ordering matters — map after = reload failure, verified live), guard with `[ ! -f ]` to never clobber the live glue map, and in remove delete it only when no other instance remains (`yunohost app list | grep -q "id: <app>__"`).
- example_ynh git modes: install/remove/upgrade/backup/restore = 100755; _common.sh/change_url/config = 100644. YNH executes via `/bin/bash -x ./script` so 644 never breaks installs — but match the standard (chmod + `git add` records the mode).
- example_ynh canonical set beyond scripts/: doc/DESCRIPTION.md(+_fr), ADMIN.md, README_fr.md, tests.toml, LICENSE, .gitignore. Catalog-level manifest `integration.sso` must be boolean or "not_relevant" — never "partial". YNH creates a default `main` permission even with no [resources.permissions] section, so `yunohost user permission update $app.main --logo` works for domainless apps too.
- Repos with no local git upstream tracking (`branch -vv` blank): `git branch --set-upstream-to=origin/main main` then pull --ff-only.

## Catalog presentation quality — manifest description + DESCRIPTION.md text rules (YunoHost/issues#2676, alexAubin; issue open, 0 comments, body is the guideline)
Founder-level catalog guideline for description TEXT (distinct from the assets/lint rules above). Applies to every package before "done":
- SHORT description (manifest `description.en`/`.fr` — the catalog tiles): concisely what the app actually IS / DOES / ALLOWS. NEVER: "free / open source / libre" or "self-hosted" (implicit for every YunoHost app); "Web app to ..." (the vast majority are web apps — say what it does instead); "[single word] management software/server/system" shapes; the build tech ("PHP webapp" — people shouldn't care); fuzzy adjectives ("lightweight", "simple", "best", "easy").
- DETAILED description (doc/DESCRIPTION.md — apps.yunohost.org/app/<id>): what it is/does/allows + a detailed feature list; pointers to related software are a plus (external mobile/desktop clients, apps it combines with); tech under the hood may be mentioned but is not the focus; no copy-pasta of upstream's description — upstream text bragging "self-hostable" is meaningless here (it wouldn't be in the catalog otherwise).
- MARKDOWN TRAPS in DESCRIPTION.md: the feature list must be a MULTI-LINE markdown list (not all items on a single line); an INDENTED list item (line starting `  -` with leading spaces) renders as a CODE BLOCK, not a bullet; section titles like "Features" start at THIRD level (`### Features`) because the file gets embedded under higher-level titles in the catalog UI.
- FR PAIRING: manifest has a french short description ⇒ doc/DESCRIPTION_fr.md MUST exist (else the catalog mixes languages mid-browse).
- SCREENSHOTS: at least one when applicable; only png/jpg are supported; "only a few hundred kB max" (end-user bandwidth); filename doesn't matter.
- SUBMISSION-TIME metadata (lives in the catalog apps.toml block, NOT the manifest): `potential_alternative_to` makes the app findable as an alternative to popular (typically proprietary/centralized) services — searching "Google" or "Google Drive" in the catalog lists the corresponding apps; the list needn't be only proprietary services. Antifeature diligence is a real check: inspect the upstream/app for third-party asset calls (Google Fonts etc.) before declaring it free of them.

## Catalog submission mechanics (official docs, checked 2026-10-26, quote-verified against live dev-doc text 2026-10-27)
- Submission PR adds the app to apps.toml in YunoHost/apps; level is set by the CI bot (opens its results PR every Friday evening; never by hand); catalog JSON (app.yunohost.org/default/v3/apps.json) rebuilds ~every 4 h. state starts `working`; category from categories.toml (the CURRENT catalog carries NO subtags — never copy `subtags` keys from stale old packages); declare antifeatures honestly.
- CATALOG AUTO-PUBLISHES `main` (official WARNING, YunoHost/apps README): once listed, the catalog publishes the HEAD of branch `main` (overridable only via `branch`/`revision` keys in the apps.toml entry) — every commit pushed to main goes live for all users at the next ~4 h catalog rebuild. Therefore: develop in separate branches, merge to main ONLY what passed the full gate suite; for org repos get the change CI-tested first (PR + `!testme`, or developer-CI access from the Apps group). A broken main doesn't just look bad — level ≤4 hides the app and freezes upgrades for every installed instance. Same discipline for hotfixes under time pressure: gate first, then merge.
- Start packages by CLONING example_ynh, not forking it (live docs: "you should not fork the example app. You will rather clone" — copy files except .git).
- Quality levels (package_check computes 0–8; ≤4 = 'bad quality', install discouraged): 0 broken · 1 installable in one scenario · 2 all install scenarios · 3 upgradable · 4 backup/restore OK · 5 no linter errors · 6 repo hosted in YunoHost-Apps org · 7 all tests + no linter warnings · 8 sustained ~1 yr. Level 6+ requires transferring the repo to the YunoHost-Apps org (GitHub Settings → Transfer ownership → YunoHost-Apps; write access via the Apps chat room).
