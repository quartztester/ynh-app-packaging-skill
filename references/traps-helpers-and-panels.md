# Helpers v2.1 / templating / config-panel traps (ynh-app-packaging)

Carved from platform-traps.md 2026-10-27 (router there). Script-writing bugs: helper names, template rendering, config panels, systemd helpers. Verify names against /usr/share/yunohost/helpers.v2.1.d/.

## Helpers: v2.1 names differ from 2.0 docs
- Helpers are NEVER shipped in the package: scripts only `source /usr/share/yunohost/helpers` (ships with YunoHost core, included in every example_ynh script). YunoHost exports YNH_HELPERS_VERSION itself = manifest `[integration].helpers_version`, falling back to packaging_format — so WITHOUT the explicit `helpers_version = "2.1"` pin a packaging_format=2 app silently loads the OLD helpers.v2.d (ynh_add_config etc.). The current example_ynh template carries the pin; keep it when editing manifest.toml.
- Loader: `source /usr/share/yunohost/helpers` with `YNH_HELPERS_VERSION=2.1` reads `helpers.v2.1.d/`. 2.0 names are DEAD: use `ynh_config_add` (not ynh_add_config), `ynh_config_add_systemd`, `ynh_config_add_nginx`, `ynh_systemctl` (not ynh_systemd_action), `ynh_safe_rm` (not ynh_secure_remove), `ynh_exec_as_app` (not ynh_exec_as), `ynh_psql_db_shell` (NO ynh_psql_execute_as_root), `ynh_restore`, `ynh_config_change_url_nginx`.
- `yunohost service add` has NO `--log_type` on YNH 12.
- Ground truth check: `YNH_HELPERS_VERSION=2.1 bash -c 'source /usr/share/yunohost/helpers; declare -F'` and `grep -n "^ynh_.*(" /usr/share/yunohost/helpers.v2.1.d/<topic>`.
- Asymmetric systemd helper signatures: `ynh_config_add_systemd` takes `--service=`/`--template=` flags, but `ynh_config_remove_systemd` takes POSITIONAL service names — `--service=` dies with "unsupported operand".
- `ynh_backup`/`ynh_restore` in helpers v2.1 take POSITIONAL paths, not `--src_path=`.
- Hallucinated helpers are caught statically: verify_conformance.py diffs every `ynh_*` call in scripts/ against the local helpers.v2.1.d definitions (a live install died on a plausible-sounding `ynh_app_log` that never existed — that failure mode is now a lint failure, run it before every push).
- `systemctl daemon-reload` bare — `ynh_systemctl --action=daemon_reload` is the v2.1 form.
- `ynh_config_add_fail2ban` with `--logpath` / `--failregex` GENERATES the jail+filter conf itself (live docs, verified 2026-10-27) — prefer flags over shipping conf/f2b_*.conf templates; either way validate the regex with `fail2ban-regex` and remember app jails must land in /etc/fail2ban/jail.d/ (jail.conf is overwritten on fail2ban package updates).
- `ynh_app_setting_set_default --key=foo` also EXPORTS the shell variable `$foo` — the sanctioned way to give tunables (php-fpm etc.) non-default defaults while staying admin-overridable.
- php-fpm: under `php_process_management = "dynamic"` the helpers define NO defaults for `$php_group`, `$php_memory_limit` (nominal 128M), `$php_start_servers`, `$php_min_spare_servers`, `$php_max_spare_servers` — they MUST be set or the fpm conf renders broken.
- Simple templating is case-sensitive (tags UPPERCASE, var names lowercase) and `__PATH__/` collapses to `/` when $path is / — templates using `__PATH__/sub` work at both root and subpath installs.
- PHP version var is `$php_version` (underscore) — the example_ynh manifest's apt comment says "$phpversion", which is WRONG/legacy: helpers.v2.1.d/php dies with "$php_version should be defined" and helpers.v2.1.d/setting auto-converts a legacy `phpversion` setting to `php_version` (for consistency with nodejs_version etc.). Always use `$php_version` in scripts (backup/restore pool paths, `ynh_systemctl --service="php$php_version-fpm"`); the apt resource exporting phpX.Y-* packages sets it.
- Never pin a phpX.Y version from memory of "the distro default" — distro PHP moves (bookworm launched with 8.2, sury/updates carry 8.4/8.5, trixie differs again). Query the target box/distro first (`apt-cache policy 'php*-fpm' | grep -A1 php`) and declare apt packages for the PHP you actually verified, or let `$php_version` flow from the helpers. Benchmark evidence: both a with-skill and a baseline run pinned php8.2-fpm blind and only escaped failure because the box happened to carry sury multi-PHP.

## Templating and env rendering
- `_ynh_replace_vars` substitutes ONLY uppercase `__FOO__` from the shell var `$foo` and `ynh_die`s if unset — lowercase tags pass through silently; every template placeholder needs a matching variable set in EVERY script that renders that template (install, upgrade, restore, config apply), including derived ones like `redis_port="$port_redis"` when the template says `__REDIS_PORT__`.
- `ynh_config_add` templates substitute from LOCAL SHELL VARS, not app settings — `ynh_app_setting_get` every var before rendering, in every lifecycle script that re-renders (loomio dogfood: `$database_url` uninitialized rendered literal `__PLACEHOLDERS__`).
- Env/dotenv templates: QUOTE every free-text value (`SITE_NAME="__SITE_NAME__"`, not bare) — a multi-word panel value renders unquoted, then every `set -a && source .env` step assigns only the FIRST word and executes the rest as a command ("Loomio: command not found" warnings mid-assets-precompile, var silently truncated; loomio dogfood 2026-10-27). Select/number keys don't need it but quoting is harmless — keep the diff minimal and quote what a user can type.
- `ynh_config_add` ALWAYS overwrites its destination (`cp -f` + re-render); a manually edited managed file is only preserved as a timestamped `.bak` sibling plus a warning in the log. Template fixes therefore DO apply on every upgrade — but live edits to managed config are silently reverted.

## ynh_restore default-permissions trap
`_ynh_apply_default_permissions` chmod-400/root-owns any restored path that is NOT exactly `$install_dir`, `$data_dir`, or `/var/log/$app` (system-file branch). Restoring `$install_dir/app` or `/etc` confs therefore breaks them unless you fix up after: chown -R app:app + `chmod -R u=rwX` for release trees; `clickhouse:clickhouse` for CH drop-ins (daemon dies 'Access to file denied'); `root:www-data 640` for nginx vhost confs (workers can't read → 404). Also reload nginx at the end of restore.

## Config panels (YunoHost 12)
- Panel must be `[main.<section>]`; `choices = ["a", "b"]` (list, not dotted dict).
- **CLI set trap (linkding dogfood 2026-10-26)**: `yunohost app config set <app> -a "key=value"` takes the SHORT option id only. A dotted path (`main.section.key`) is silently DROPPED while the command still prints "SUCCESS ... Config updated as expected" — a fully green no-op. Never gate a panel change on the CLI exit status; re-read the effect (settings.yml entry, rendered unit env, service state) instead. Values reach scripts/config as env vars NAMED BY THE SHORT ID (booleans serialize as "0"/"1"), and overriding `ynh_app_config_apply()` REPLACES the generic bind=settings auto-persist loop — a custom apply must do its own `ynh_app_setting_set` + template re-render for every key it owns.
- bind syntax: `"KEY:/path/file"` (key FIRST when it differs from question id), `"settings"` for app-settings-bound values, `":/path"` when key == id. A wrong bind parses as a new bind target → 'File does not exists'.
- `scripts/config` must end with `ynh_app_config_run $1`; override `ynh_app_config_apply() { _ynh_app_config_apply; ...extra... }` for post-apply actions.
- **scripts/config argument is `show`/`apply`, never `get`/`set` (loomio dogfood 2026-10-27)**: a post-apply re-render hook written as `if [ "$1" == "set" ]` NEVER fires — the panel machinery invokes the script with `apply`, the hook is silently skipped, settings.yml updates but rendered config/env stays stale while the command still reports SUCCESS. GATE a panel round-trip on the RENDERED FILE's content, not the CLI exit. (CLI set syntax on YNH 12.1: `yunohost app config set <app> <key> -v <value>` or `-a "k=v&k=v"` — the bare `app key=value` positional form dies with "filter key ... incorrect", and a value with spaces must be inside the `-a` string or `-v` arg.)
- Nested keys bind as `"foo>max:__INSTALL_DIR__/conf.json"`; whole-file bind (no colon, e.g. `bind = "__INSTALL_DIR__/config.ini"`) for `file`/`text` questions; `bind = "null"` for custom logic.
- Custom getters/setters/validators: `get__key`/`set__key`/`validate__key` in scripts/config (raw stdout, or YAML for choices/alert styling; escape-quote raw values containing `#`). Actions: `type = "button"` + `run__key()`; `visible`/`enabled` are JS expressions over the section's values (incl. `match(v,'regex')`).
- Short keys must be UNIQUE across the whole config_panel.toml (not per section). FORBIDDEN short keys: old, file_hash, types, binds, formats, changed; avoid settings names (id, install_time, mysql_pwd, path, domain, port, db_name, current_revision, admin) unless that's exactly what you mean to bind.
- TOML table-collision (privatebin 2026-10-27): a section TITLE (`name.en`/`name.fr` under `[main.<section>]`) implicitly creates the `<section>.name` table, so a QUESTION with short id `name` in that section then re-declares it — `tomllib.loads` dies with "Cannot declare ('main','<section>','name') twice". Either drop the section title (sections render untitled) or rename the question id; validate every config_panel.toml with `python3 -c 'import tomllib; tomllib.loads(open("config_panel.toml").read())'` before committing.
- RUNTIME panel collision, TOML-clean (privatebin benchmark 2026-10-27): a question with short id `name` under an UNTITLED section passes `tomllib` but YNH's ConfigPanel pydantic model still rejects it — `yunohost app config get` dies with `Error while parsing config panel: str type expected` (the model wants `sections -> name` as str, finds the question table). Any section-model field name (`name`, `services`, …) is unusable as a question short id even when TOML parses clean. TOML validation is INSUFFICIENT as a panel gate — the only reliable gate is a real `yunohost app config get <app>` (or `app config set` round-trip) on an installed instance.
- Every non-null-bind question id should correspond to an app setting reused by install/upgrade — otherwise panel writes and ynh_config_add templates diverge.
- Optional install questions need `optional = true` in the manifest (an empty default is not enough).
- **scripts/config env-var clobber (qbittorrent benchmark 2026-10-27)**: the panel machinery delivers submitted values to `scripts/config` as env vars NAMED BY THE SHORT ID. NEVER re-read settings into those names at the top of the script (`webui_localhost_auth=$(ynh_app_setting_get ...)` clobbers the submitted value) — the apply becomes a silent no-op: setting never persists, no functional change, while the CLI still prints "SUCCESS ... Config updated as expected". Read settings ONLY under names no panel question uses (or inside setters, after the machinery has persisted).
- **Panel booleans serialize as "0"/"1" (qbittorrent benchmark 2026-10-27)**: when a panel value feeds an app's own config file with a different boolean vocabulary (qBittorrent INI wants `true`/`false`), translate explicitly (`case ... 1|true) ...`). Writing 0/1 raw gets silently normalized away by the app — the toggle stays inert in one or both directions.
- **Apps that rewrite their own conf from memory race the panel apply (qbittorrent benchmark 2026-10-27)**: qBittorrent-nox rewrites qBittorrent.conf on shutdown from IN-MEMORY state, so a file patch made while the daemon runs is reverted by the very restart that follows (proven: patch `LocalHostAuth=true` → `systemctl restart` → value back to empty). For such apps the panel apply must `stop` the service, patch, then start (let the `services = [...]` machinery do the start) — patch-then-restart silently loses the change.
- **`ynh_systemctl --wait_until` patterns must match the REAL journal output of the version you ship (qbittorrent benchmark 2026-10-27)**: a baseline package waited for `qBittorrent v.* started`, a line qb 4.5.2 NEVER prints (actual: "WebUI will be started shortly after internal preparations") — deterministic install hang (4x normal time), CLI killed by timeout, YNH rollback left a half-registered app. Verify the exact line from a scratch run of the pinned version before writing the pattern.
