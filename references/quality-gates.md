# Quality gates & full workflow detail (ynh-app-packaging)

Moved verbatim from SKILL.md on 2026-10-26 when the skill was slimmed to a lean rule set. Load when actually gating a package.

## When to Use
- "Install <app> from GitHub" requests: check for an EXISTING `$GH_ACCOUNT/<app>_ynh` package FIRST (`api.github.com/users/$GH_ACCOUNT/repos` filtered on `_ynh`) — the user usually means their own package, not upstream. Never stand up an upstream Docker route while that `_ynh` exists (proven 2026-10-26: a full ghcr pull was torn down after finding the existing package).
- Writing a new YunoHost app package (manifest.toml, scripts/, conf/).
- Debugging install/upgrade/backup/restore/config-panel failures on YunoHost 11+/12.
- Deciding subdomain vs subpath for an app, or binding app config to env files.
- Diagnosing why a catalog/third-party `_ynh` repo lags upstream or whether its auto-update bot runs → `references/upstream-repo-staleness-triage.md` (gh-api triage recipe; apt-installed apps have no bot-updatable sources at all).

0. SMOKE-TEST UPSTREAM FIRST: clone/fetch the upstream source, run it once outside YunoHost (scratch port + throwaway creds/keys) and exercise login + the core API with curl before designing the package — it settles route map, env vars, and required services cheaply. Delete any scratch state (e.g. `redis-cli --scan --pattern 'prefix:*'`) afterwards.
0a. BASIC-FUNCTIONALITY GATE (user directive 2026-10-14, after the watcharr login-loop escaped to production): "install green + endpoints 200" is NOT done. Before reporting any web app packaged: in a REAL browser with a REAL portal login (throwaway yunohost user, deleted after), exercise the app's PRIMARY WRITE PATH end-to-end — log in, perform the app's core action (add an item / post a comment / change a setting) through the UI or the page's own fetch context, and CONFIRM the result renders on reload. Watch the URL for bounce loops between the app root and its login page for ~15s. A token-mint (POST /api/auth/proxy 200) is NOT proof of working auth: the NEXT authed request is where header clobbering shows. Anonymous curls that 302 to the portal prove nothing about static serving either — the ssowat redirect MASKS any 403/404 behind it: assert the nginx worker can actually serve the SPA root with `namei -l <served index.html>` (every directory in the chain needs the traverse bit) and `sudo -u www-data head -c 1 <served index.html>`. Build output dirs (vite `dist`) are created 0750 owned by the build user and 403 every authed visit while every anon test looks green — every script that builds (install/upgrade/restore) must `chmod -R o+rX` the served output dir itself, not just the parent chain. Clean up test rows + throwaway user afterwards.
0b. MAIL-SEND GATE (user directive 2026-10-27: "make sure the skill integrates the yunohost mail server if needed; wire SMTP and have it as a test case"): for any app that sends email, wiring is NOT done until a REAL app-level send has been triggered and traced through the box's Postfix. Defaults: SMTP 127.0.0.1:25 plaintext no-auth (SKILL.md rule 11); From = `app@<install-domain>` unless the box relays outbound through a verified external domain (then that domain). Procedure + traps (string-truthy SSL flags, no-op sends for unknown emails): references/postfix-integration.md §Outbound. Pass = app 2xx without mailer exception + mail.log `from=<app@…> queue active` + relay handoff `status=sent`. Run it in the install functionality gate AND after restore (env re-render can silently drop mail config).
0c. ENDPOINT-MATRIX GATE (umami iteration-7: a public permission silently portal-walled every analytics endpoint while all other gates stayed green): after install, after restore, and after any change_url, enumerate the app's permissions from `/etc/ssowat/conf.json` (`python3 -c` + json — per permission: uris, users, auth_header) and assert BOTH directions with anonymous curl (no cookie, no credentials): (a) every permission whose users include `visitors` must serve at least one representative URI per entry WITHOUT a 302 to the portal — record the expected code (200/204/405-by-design) but the hard rule is never-302; (b) every protected permission's URI must 302 (or 401) anonymously — proves the wall exists. Regex `re:` URIs are the known failure shape (`re:^/` never matches host+path — ssowat-integration.md §anchoring): a public permission whose regex never fires looks perfectly configured in `yunohost user permission list` while dead in production. Cookie-less probes only (portal cookies mask 302s).
0-feas. FEASIBILITY PROBE (when the user asks 'would X be easy to package?' / 'initial impression, do not start anything'): answer from cheap evidence, not recall — (a) curl the upstream download page and grep for asset URLs, then download the Linux tarball to scratch and `tar tzf` it: one call settles arch-independence, size, runtime deps (bundled JRE? per-arch binaries?), and whether the URL is a rolling-latest (bad for manifest pinning → mirror as GitHub Release asset); (b) enumerate the upstream GitHub org (`api.github.com/search/repositories?q=<app>`) with stars + pushed_at to find official plugins/API surfaces and which are still alive; (c) curl the app's integration surfaces (RPC ports, hosted UIs) for a live 200 check; (d) check whether the *arr suite / existing catalog packages already speak to the app natively — an integration gap there, not the runtime packaging, is usually the real cost driver. Report a short verdict; install nothing. Verified app-specific notes live in `references/biglybt.md` (BiglyBT feasibility probe worked example).

## Standard workflow (user's default expectations)
0b. ALWAYS START FROM example_ynh — NO EXCEPTIONS. Never hand-write manifest.toml or scripts/ from memory or by copying an old package's layout. Bootstrap every new `<app>_ynh` by unpacking the template skeleton, then edit in place:
   ```bash
   mkdir -p $WORKSPACE/<app>_ynh && tar xzf <skill_dir>/templates/example_ynh-snapshot.tar.gz -C $WORKSPACE/<app>_ynh
   ```
   This guarantees the full file set ships (README.md/README_fr.md, doc/PRE_INSTALL.md + PRE_UPGRADE.md + POST_UPGRADE.md + _fr variants, LICENSE, .github templates, .gitignore/.gitattributes/.editorconfig — all routinely forgotten when scaffolding from an old package). Refresh the snapshot from upstream before starting a new package (`git clone --depth 1 https://github.com/YunoHost/example_ynh`, re-tar without .git) — the template and helper conventions evolve; a snapshot older than a few weeks is a bug source. When converting an existing half-done package, diff it against the snapshot (`diff -rq` after excluding conf/ and app-specific files) and adopt any template file the package lacks.
1. AUTHORITATIVE REFERENCES FIRST (standards evolve — re-fetch, don't recall): official docs https://doc.yunohost.org/en/dev/packaging (LIVE tree, re-audited 2026-10-27; helpers/resources pages auto-generated 2026-09-03 from YunoHost 12.1.41.1; all pages distilled and indexed in references/official-docs.md) and the example app https://github.com/YunoHost/example_ynh (structure, manifest keys, helper usage). Cross-check helper names against the installed helpers (`/usr/share/yunohost/helpers.v2.1.d/`). LINT LESSONS (fleet audit, 2026-10): (1) the banner-title regex must allow `: " ~ _` or valid ALL-CAPS titles get flagged; (2) helper-call extraction must require command position (not inside paths/strings/option values) and whitelist functions defined in the repo's own scripts/, or filenames like `ynh_sso_login.lua` and locally-defined wrappers count as hallucinations. DEV ENVIRONMENT: the docs' sanctioned test bed is a disposable LXC/Incus or VirtualBox VM (ynh-dev is Incus-based; snapshot freely, package_check parity, zero production risk) — see references/official-docs.md §Dev environments; LOCAL package_check dry-run recipe (same harness as official CI, incl. the Docker-conflict trap): official-docs.md §13; the live-box procedures in this skill are the production-server workflow for when no dev VM exists.
2. NATIVE PACKAGING ONLY — no Docker containers (user policy: YunoHost packaged apps first-class; Docker only when no native option exists, which for packaging means never).
3. SSO BY DEFAULT: any app with its own login gets the SSOwat bypass pattern (see references/ssowat-integration.md) so users walk straight in with their YunoHost credentials, Nextcloud-style.
4. PUBLISH TO GITHUB by default under `$GH_ACCOUNT` (PAT `$GH_TOKEN_FILE` 600; author `$COMMIT_AUTHOR`; never the user's real name/email). NEVER embed the PAT in a remote URL — it persists in .git/config on every clone/machine; the credential.helper wired to `$GH_TOKEN_FILE` authenticates plain https URLs, so `git remote set-url origin https://github.com/<owner>/<repo>.git` is both cleaner and leak-proof. Repo name: prefer the FULL upstream project name `<upstream-name>_ynh` (user renamed a short-id repo to match upstream — match upstream's GitHub repo name when it exists); the installed app id is a separate, narrower thing: `[a-z0-9_]` only, no hyphens, so a hyphenated repo name needs a short app id and that mismatch is fine/expected. Renaming a published repo: `PATCH /repos/<owner>/<repo>` with `{"name":...}` (old URL auto-redirects), `mv` local dir, update remote URL + README references, `git tag -f` + `git push -f` the release tag. For changes to an ALREADY-published repo made during live server work: deploy and verify on the box, commit locally with the quartztester identity, and wait for the user's explicit approval before pushing — GitHub publication of server-driven changes is user-gated. Host source tarballs + any apt keys as GitHub Release assets (self-hosted mirrors add DNS/hairpin failure modes). Tag v<version>-ynh<N>.
5. VERIFY the full lifecycle before reporting done: install → config panel get/set → backup → remove → restore → upgrade (-u <repo>) → same-version upgrade AGAIN (double-upgrade proves scripts survive non-fresh state; see Upgrade-durability doctrine) → CHANGE_URL MOVE (below). All rc=0, public endpoints + auth surfaces curl-checked. Then linter (package_linter.py) clean except 'not in catalog', with the linter OUTPUT pasted into the REPORT — "ran the linter" is an assertion, the ✘/✔ lines are evidence. Test tooling (live docs, verified 2026-10-27): preconfigure install answers with `-a "&domain=…&path=/…&init_main_permission=…"` (ampersand-separated); `--no-remove-on-failure` keeps a failed install on the box for autopsy; `--force` skips unsafe/low-quality confirmations; `yunohost … --debug` for verbose operation logs; dev-CI runs from PR comments (`!testme` posts a .png summary).
CHANGE_URL MOVE (umami iteration-7: every package ships scripts/change_url and no gate ever ran it): after the upgrade double-pass, move the LIVE install once and prove it survived — subpath-capable app: `yunohost app change_url <app> -d <domain> -p /newpath`; full-domain app: move to a second registered domain on the box — none exists? `yunohost domain add <test-domain>` first (fresh domains carry a SELF-SIGNED cert until `yunohost domain cert install <d> --no-checks` runs and DNS resolves; click through the browser interstitial once per tab). Then re-run §0c endpoint matrix + §0a functionality gate + read a pre-move canary (change_url must relocate, not touch data). Move back (or keep the new location and re-verify the portal tile followed). Watch: permission URIs that embed the old path (regex or plain), app config with absolute URLs (ROOT_URL, redirect URIs, CSRF/origin allowlists), nginx map entries, ssowat conf regen. A package whose change_url was never executed by its author is an untested script shipping to every user who renames their install. Re-pin mechanism: permission URIs move via the `ynh_permission_url` HELPER — NOT `user_permission_update(url=…)` (no such kwarg in YNH 12; the TypeError hits mid-script AFTER app-side absolute URLs were already rewritten, leaving a half-moved app: nginx rolled back, app pointing at the new domain — verified live listmonk 2026-10-28). Order change_url writes so app-side absolute-URL updates come LAST. An app that fundamentally cannot move (hardcoded absolute URLs, domain-bound identity): don't fake the gate — pin the constraint in tests.toml args, exclude `change_url` by real test ID (live list, verified 2026-10-30: install.root / install.subdir / install.nourl / install.multi / backup_restore / upgrade.<commit> / change_url), document the limit in doc/ADMIN.md, and prove the admin fallback instead: backup → remove → reinstall → restore.

REINSTALL GATE (added 2026-10-30: CI runs install/remove/reinstall as a scenario; the local gate list never chained them — every package ships install+remove): after the b/r chain, plain `yunohost app remove <app>` (data dir retained by design), fresh install from the clone, re-run the functionality gate, and read a data-dir canary created before the remove (files must survive; settings do not — secrets regenerate, re-render env from settings, never trust retained copies). Catches what restore hides: stale services/users/nginx maps/ports from a dirty remove, install scripts assuming an empty data dir, retained-data vs rotated-secret mismatches. Purge (`rm -rf /home/yunohost.app/<id>*`) only between diagnosing retries or benchmark arms — the gate itself mirrors CI and keeps the data. For multi_instance=false apps this replaces install.multi as the second-install proof (CI skips that scenario when the manifest declares false).

MULTI-INSTANCE DECISION RULE (manifest integration.multi_instance — canonical home; catalog evidence 2026-10-30, all 723 catalog manifests crawled): 72% of the catalog declares true; false is legitimate AND level-compatible (wireguard, searxng, mytinytodo are L8 false) — package_check runs install.multi only when true, so false needs NO tests.toml exclude. Decide:
- TRUE is the default: helpers suffix every dir/user/db/port with $app and the second install auto-names app__2. Site-per-install apps (static generators, CMS, the my_webapp model — ONE site per instance, second site = second install; no catalog app ships a multi-site config surface) are always true.
- FALSE only when the app holds a machine-global resource the $app suffix cannot isolate: kernel/network state (VPN, tunnels), protocol-fixed ports that peers or clients hardcode (53, 5222/5269, 3478, 51820, 1935, DLNA, BitTorrent), mail-stack hooks (postfix/dovecot), system-state mutation (firewall, monitoring agents, backup target, containers), hardware binding (USB dongle, tuner, UPS). State the reason in a comment on the manifest key AND in doc/ADMIN.md — grade_static.py fails false-without-reason.
- "Nobody would install two" is NOT a reason (federation apps split both ways: synapse true, peertube false) — only "a second install breaks or clobbers" counts.
- YNH 12.1 does NOT enforce the flag at install (official-docs.md §15.6): a second copy installs as app__2 with suffixed dirs/users but UNSUFFIXED global state, clobbering the first or dying half-registered. A false package must therefore SELF-GUARD: install fails fast when the resource is already claimed (port bound, interface/hook/config present), and passes the REINSTALL GATE above.

- PostgreSQL apps MUST apt-pin the server: `[resources.apt] packages = ["postgresql"]` — `DatabaseAppResource.provision_or_update` provisions db/user only and NEVER installs the server (read from YNH 12.1 utils/resources.py); a PG app relying on the DB resource alone dies on stock boxes. MariaDB needs no pin (core dependency). Enforced by scripts/grade_static.py.
QUALITY LEVELS (official, 0-8): 0 broken · 1 installable in ≥1 scenario · 2 all scenarios · 3 upgradable · 4 backup/restore works · 5 no linter ERROR · 6 in YunoHost-Apps org · 7 all tests pass + no linter warning · 8 maintained long-term. Level ≤4 = "bad quality" → app HIDDEN from the catalog and upgrades PUT ON HOLD for every installed instance. Levels are BOT-assigned (official CI PRs every Friday evening; catalog apps.json rebuilds every 4h) — never manually claimed. The gates in this file exist to keep a package at level ≥7; catalog visibility is the stake.
6. CATALOG-READY EXTRAS (HARD GATE — user complaint 2026-10-15: repos keep shipping WITHOUT a logo or screenshots; a package is NOT done until both exist): `logos/<appid>.png` — square RGBA PNG ≥180px (prefer 512), transparent corners (verify by decoding IDAT corner alpha, `file` lying 'RGBA' is not proof); a repo pushed with no logos/*.png is a bug. `doc/screenshots/*.png` — REAL rendered images (a doc/screenshots/README.md stub referencing a nonexistent .png = zero screenshots); embed them in README.md+README_fr.md under `## Screenshots` as `![alt](./doc/screenshots/x.png)`. Also ship the full example_ynh file set: README_fr.md, doc/DESCRIPTION_fr.md, ADMIN.md+ADMIN_fr.md, POST_INSTALL.md, PRE_INSTALL.md+PRE_INSTALL_fr.md, PRE_UPGRADE.md, POST_UPGRADE.md, .gitignore, tests.toml, LICENSE — the REAL upstream license text, never the example_ynh placeholder left by the snapshot (fetch upstream's LICENSE/LICENSE.txt via its repo tree or package_linter ✘'s it); script modes 755 for install/remove/upgrade/backup/restore, 644 for change_url/config/_common.sh. README regenerated via apps-tools/readme_generator/make_readme.py. Submission PR adds entry to YunoHost/apps apps.toml + logos/ (state=working, category from categories.toml) — only when the user asks to submit to the catalog. Description TEXT quality follows repo-hygiene.md §Catalog-presentation-quality (YunoHost/issues#2676): short desc = what it does, no "self-hosted"/"web app"/tech/fuzzy-adjective filler; DESCRIPTION feature list a multi-line markdown list with `###` titles (indented `-` renders as a code block); fr short description ⇒ DESCRIPTION_fr.md exists.

## Admin-GUI standard for packaged apps (standing user preference)
The packaging standard the user holds GUIs to: "The admin should not have a PhD in computer science to be able to install, configure and use your application." For any web GUI shipped in a package:
- Default surface is a friendly editor, never a raw config file: plain-language action dropdowns ("Block them", "Show them the challenge"), labeled toggle chips for upstream presets with one-line plain-English effects, human summaries per rule ("visitor IP in 10.0.0.0/8"). Raw file editing lives only in a collapsed "Advanced" section as the escape hatch, with a link to upstream docs.
- Saving from the friendly editor must preserve what it does not model: parse the live config, replace only the modeled subtree, dump — never rebuild the whole file from the form.
- Round-trip identity is a hard gate: parse → view → save with NO edits must reproduce the config exactly. Ship a self-check asserting build(view(doc)) == doc against the live config before trusting the editor — it catches rules whose matcher data the view silently dropped.
- Keep the editor's state as one JSON blob server-rendered into a `<script type="application/json">` block and build the save payload from that blob — never reconstruct it by scraping data-* attributes off server-rendered rows. Rows without their matcher data save as name:null and the backend rejects the entire save.
- Entries the form cannot express (geoip, asns, expression matchers, header maps) must round-trip verbatim as opaque entries with a distinct "YAML only" badge — silently dropping them changes live protection. A matcher the backend always rejects (e.g. headers_regex needs a mapping while the form sends a string) must not appear in the friendly form at all; leave it to the YAML editor.
- One page, not many: merge config panels into the app's main page below the primary list; do not send the admin to a second URL (old routes 302 back to the main page).
- Ship a "Restore defaults" action that reinstalls the pristine config from the app-registry copy (/etc/yunohost/apps/<app>/conf/, refreshed by every upgrade) THROUGH THE SAME validate + dry-run pipeline as a normal save, and confirm before applying. State what it keeps (domains, difficulty) vs what it discards.
- Warn before losing unsaved work: track a dirty flag PER SAVE TARGET (domain toggles + numeric settings, structured rules, raw YAML), show a visible "unsaved changes" banner, and register a beforeunload handler (e.preventDefault() + returnValue) while ANY flag is set. Clear a flag only on that target's successful save response; a restore-defaults that reloads the page clears all flags before the reload. Keep the flags per-target INTERNALLY (a failed save of one target must not lose another's) but expose ONE save action: a sticky bottom bar (Save changes + Discard) that saves every dirty target in sequence, toasts on success, and reports failures inline per section — never alert(). Multiple section-local save buttons (Apply / Save rules / Save YAML) are the top confusion signal on settings pages: the user cannot tell which button covers which control. Ctrl/Cmd+S triggers the same save.

## Verbosity / over-engineering audit of *_ynh repos (report-only; run when user asks to audit packages for bloat/verbosity)
- Profile first, read only outliers: `find <r>/scripts <r>/conf -type f | xargs wc -l` per repo + custom-function inventory `grep -hE '^[a-zA-Z_]+\(\)[[:space:]]*\{' <r>/scripts/*`. Repos with zero custom functions and <~600 LOC are almost always already lean; spend the read budget on files with custom functions or outsized installs.
- Unused manifest settings: extract `[install]` TOP-LEVEL keys only — regex on the definition line `^\s*(\w+)\s*=\s*\{.*\btype\b` — then grep each name across scripts/. Naive per-line key extraction catches TOML subkeys (`type`, `default`, `optional`, `choices`) and reports every subkey as an unused setting — 100% false positives.
- Duplication measurement: strip comments/blank lines then `comm`/`diff` install vs upgrade bodies — 50%+ identical lines means extract one shared `_app_deploy()` into `_common.sh` with two thin callers. Cross-script function copies: `diff <(sed -n '/fn()/,/^}/p' scripts/install) <(sed -n '/fn()/,/^}/p' scripts/restore)` — empty diff = verbatim copy, consolidate into `_common.sh`.
- Dead codepaths: anything under scripts/contrib/ not referenced by any lifecycle script (`grep -rl <name> <r> | grep -v contrib` → only README hits) is an untested second codepath that rots — flag for deletion unless the user actively uses the manual workflow it enables.
- DO NOT flag v2.1 idioms as hand-rolled: `conf/systemd.service` + `ynh_config_add_systemd`/`ynh_systemctl` IS the platform pattern (absence of any `ynh_systemd_create` call is correct, not a miss); the 3-7 line `ynh_app_config_apply() { _ynh_app_config_apply; ... }` override shim is required for settings-bound re-render; a bounded curl health-wait loop is legitimately hand-rolled (v2.1 ships no wait-for-port helper) — but N copies of the same loop across install/upgrade/restore/config collapse into one `_common.sh` helper.
- Output format the user expects (ponytail style): one ranked line per finding `<tag> <what to cut>. <replacement>. [path]` with tags delete/yagni/native/shrink, `net: -N lines` at the end, findings only — apply nothing unless the user says so.

## Reviewer-maintainability rule (official YunoHost policy — generated packages get REJECTED at catalog submission)
Verbatim from YunoHost's packaging submission rules (now CONFIRMED in the live dev docs, packaging/ root page, 2026-10-27): "It might be tempting to use generative AI, LLMs, to generate app packages. Such 'contributions' have systematically brought too verbose code and comments, helpers hallucinations, non-standard directory architectures and files. Reviewing such packages is tiresome for the contributors. It has been decided to reject generated packages that do not follow the example_ynh template app." And the maintainer philosophy: "You can't just throw something you don't even understand yourself at other people, and expect them to maintain it for you."
Concrete bar for every package written or edited by an LLM (incl. this agent):
- example_ynh IS the architecture: same file set, same names, same v2 helper idioms (`ynh_config_add*` + `ynh_app_config_apply`, `ynh_systemctl`, `ynh_config_add_systemd`). No invented/hallucinated helpers — verify every `ynh_*` call exists in the installed `/usr/share/yunohost/helpers*` before using it.
- Lean, not verbose: no tutorial-prose comment walls, no defensive branches with no failure scenario behind them, no hand-rolled re-implementations of what a helper already does, no duplicated logic across install/upgrade/restore (shared code goes in `_common.sh`), no speculative settings/config the scripts never read. If a reviewer (a human YunoHost contributor who did not write it) cannot follow a script top-to-bottom in one read, it's not done.
- Every abstraction must have earned its keep (2+ callers or real complexity hidden); prefer deleting a clever indirection over documenting it.
