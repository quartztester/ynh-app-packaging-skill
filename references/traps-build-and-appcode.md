# Build-stack and app-code traps (ynh-app-packaging)

Carved from platform-traps.md 2026-10-27 (router there). Compile-time toolchain failures and app-level behavior bugs (auth, demo modes, throttles, mail flags) that only surface at runtime.

## JS build toolchains: engine pins, patch generation, scratch repro
- npm 11 ENFORCES `engines`/`devEngines` (`onFail: error`) against the node and npm actually running. Upstreams pin exact tool versions (e.g. npm `"11.16.0"`) that the nodejs resource's bundled npm doesn't match → EBADDEVENGINES kills `npm ci`/`npm run` mid-build. The pin lives in FOUR files per workspace (package.json `engines` + `devEngines.packageManager.version`, package-lock.json root `engines`), and monorepos duplicate the set across sibling workspaces (vue/ + hocuspocus/ style): grep the extracted tree for the exact pin BEFORE patching — fixing only the file named in the error leaves a sibling dying three commands later. Relax exact → caret (`"^11.16.0"`) so the newer bundled tool passes; ship as `patches/<source_id>/`.
- NEVER hand-write a multi-hunk patch: a hunk header whose line-count doesn't match its body makes `patch` swallow the next `--- a/` header as hunk context — well-formed hunks then fail with nonsense offsets. Generate instead: pristine copy `a/`, sed-modified copy `b/`, per file `diff -u a/f b/f` with the two header lines rewritten to `--- a/f` / `+++ b/f`, concatenated. Gate: `patch -p1 --dry-run` (zero fuzz) + real apply + re-run the previously-failing command BEFORE relaunching an install.
- Attribute a failure to the exact command in a `cmd1 && cmd2 && cmd3` build chain before fixing anything: read the op log AROUND the error — the success output of an earlier step (e.g. `✓ built in 1m 30s`) directly above the error names the boundary; minutes of runtime before the error are downloads/work, not an upfront check failing.
- When a failed install already rolled back (app dir and nodejs resource deprovisioned, npm debug logs gone): reproduce the failing command in scratch with the SAME toolchain — fetch the same node build from nodejs.org — and verify `node --version` shows it before trusting the repro. The npm wrapper resolves `node` from PATH, so npm 11 accidentally running under an older system node throws a misleading EBADDEVENGINES on `runtime`. A scratch repro with retained logs beats re-running blind installs.
- Build-stack apps (ruby/bundler + node/npm + assets:precompile, ~15 min install): re-running the FULL cycle per bug is the only honest gate — 10 distinct failure classes surfaced only at their exact stage (apt package naming, env placeholder init, npm devEngines exact pins in BOTH package.json and package-lock.json root, bundler `config set` arg splitting, v2.1 keyword-only `ynh_user_get_info`, heredoc-into-rails-runner newline collapse, logrotate positional args, systemd double-`bin/` paths).
- Bundler config arg splitting: `bundle config set --local path vendor/bundle without 'development:test'` collapses into one literal path string — split into separate `bundle config set --local path` and `--local without` calls.

## Python wheels + system-user npm/git (runtime deps, not build stacks)
- A wheel fetched via `resources.sources` must keep a PEP 427-valid filename (`name-version-py3-none-any.whl`) after `rename` — the provisioner validates wheel names and kills the install with exit 1 and an EMPTY operation log (no error line in the op YAML either).
- Run npm and EVERY git command as the app user inside ONE `sh -c "cd '$app_owned_dir' && …"` — git stats its CWD even for `git config`, and YNH runs scripts from a root-owned staging dir (`fatal: failed to stat … Permission denied`). Wrapping only the npm call leaves the config lines dying.
- Point the app user's HOME at the install dir, not the data dir, for npm/git runs — `git config --global` writes `$HOME/.gitconfig` and npm writes `$HOME/.npm`/`.cache`, and an app with an empty-dir init contract or a data-tree walker rejects unknown files. Keep only the `cd` aimed at the dir the tool needs.
- Rewrite git-SSH to HTTPS in the app user's global git config before `npm install` (`url.'https://github.com/'.insteadOf 'ssh://git@github.com/'`, plus the `git@github.com:` short form) — system users have no SSH keys, and TRANSITIVE deps carry git URLs even when the direct manifest is clean.
- Apps whose CLI refuses init in a non-empty dir (ArchiveBox): init BEFORE rendering package.json/node_modules into the data dir — whatever allowlist exists covers npm artifacts, nothing else.
- npm extractor binaries crashing on distro Node (WebSocket/ESM errors on Node 18) are warnings unless npm exits non-zero — check the exit code and what the official package ships before pinning a Node version.
- **Python services that log to files need `Environment="PYTHONUNBUFFERED=1"` in the unit**: python block-buffers stdout on a non-tty, so the readiness line sits in the buffer while stderr lands in the log — `ynh_systemctl --wait_until` then times out on a HEALTHY, serving app (py-spy showed `serve_forever` while the gate starved; the same binary printed its banner instantly under `PYTHONUNBUFFERED=1`). When a readiness wait times out, dump the live process stack (`py-spy dump --pid <pid>`) BEFORE concluding the app is broken — a healthy stack means the gate's pattern or stream routing is wrong, not the service. Any `--wait_until` pattern must be verified against the stream the helper actually tails, through the UNIT, never a manual shell run — and v2.1's `ynh_systemctl` defaults `--log_path` to `/var/log/$app/$app.log` (the file), not the journal.

## App-level runtime behavior (auth, sessions, throttles, demo modes)
- SPA apps move login off the classic Devise form path — discover the REAL endpoint before curling (`bin/rails routes | grep -iE 'session|sign_in'`, then read the sessions controller for the param shape); POSTing /users/sign_in when the app wants a JSON API route returns a bare 404/422 that names nothing. Auth verification without typing passwords: POST the real endpoint with the password read from a 600 root file expanded by the shell (`PW=$(cat /root/.x); curl -d "password=$PW"`), never printed. Loomio shape: `POST /api/v1/sessions` (JSON `{"user":{email,password}}`) with the `csrftoken` cookie value echoed in `X-CSRF-Token` (grab from the SPA page's Set-Cookie jar); wrong params or missing CSRF return bare 422. Authenticated data proof: an authenticated GET on a canary resource with the session cookie.
- **Upstream "demo mode" can auto-enable on production**: Loomio's `demo_groups_enabled?` is true whenever `CANONICAL_HOST` is set — a recurring EnsureDemoQueueWorker seeded @oatmilk.example demo users onto the PUBLIC install ~90 min post-restore (passwordless ghosts, but user-directory pollution). Package must ship `LOOMIO_DISABLE_DEMO_GROUPS=1`; grep any packaged app for demo/trial/sample toggles gated on config that self-hosted setups always set, and verify the users table stays clean hours after install — a recurring job fires long after your install gate passes.
- **Rack::Attack-style login throttles masquerade as "wrong password"** (loomio, 2026-10-27): after ~10 failed logins the endpoint 429s, and the SPA renders it with the SAME invalid-credentials message — the user keeps "failing" with the CORRECT password and you chase a phantom credential bug. nginx access log is the tell (401s flipping to 429s). Loomio counters live in SolidCache (postgres `solid_cache_entries`, bytea keys like `production:rack::attack:<id>:sessions/email:<email>`) — clear with a targeted DELETE, no service restart. Check the rate-limit initializer for per-email/per-IP caps before declaring any login flow broken.
- App-level CLIs invoked outside systemd (bin/rails runner, occ, manage.py) die on env the UNIT injects (DATABASE_URL etc. — a 'Could not load database configuration' error names nothing): reproduce the unit's EnvironmentFile + PATH — `sudo -u $app bash -c 'set -a; source $install_dir/.env.production; set +a; export PATH=<resource bin dirs>:$PATH; bin/rails …'` — or use `ynh_spawn_app_shell` for interactive digging.
- **Mail wiring (loomio, 2026-10-27)**: `SMTP_USE_SSL=0` made the Rails mailer open implicit TLS on localhost:25 (`OpenSSL::SSLError wrong version number` → 500 on the send endpoint) because the app reads the flag as presence (`ENV[..].present?` — `"0"` is truthy). Render string-truthy flags EMPTY when off. Full recipe + From-domain/relay rules + the three-line mail.log proof: references/postfix-integration.md §Outbound. Mail endpoints also silently no-op for unknown emails (login_tokens only mails ACTIVE users) — an app 2xx is not a send.
- Header-auth apps: pointing the app's logout URL at `/yunohost/sso/?action=logout` closes the loop end-to-end (verified in-browser: app logout → portal logout). SSOwAt also passes `Authorization: *** through on public permissions — a `url = "/api"` permission with `allowed = ["visitors"]`, `auth_header = false` gives token-authenticated REST access alongside portal-gated UI.
- Subpath installs (`path=/foo`) break apps with hardcoded absolute redirects (Plausible: /register, /sites) — check the router before allowing non-root paths.

- NEVER ship a `Content-Security-Policy` header from nginx when the app embeds its own meta CSP — browsers intersect ALL active policies and the most restrictive wins (privatebin benchmark 2026-10-27: a baseline package copied an "upstream-recommended" header CSP with `connect-src 'none'` over the app's meta CSP `connect-src * blob:` → every fetch/XHR blocked → paste creation silently impossible while the page loaded fine and 31/31 static checks passed). If the app ships its own meta CSP, ship NO CSP header from the package. If you add one anyway, runtime-test the app's primary write path afterward — static checks and render simulations cannot see this failure class.

- **Defense in depth for gated admin UIs (qbittorrent benchmark 2026-10-27)**: even when SSO/permission gates the WebUI and the app trusts localhost, SET the app's own admin password/hash at install. A baseline package left qBittorrent's WebUI at the default `admin`/`adminadmin` — and the daemon PRINTS "The Web UI administrator password has not been changed from the default" to the journal, readable by any local process. SSO gating is the outer wall, not the only one.

## Composer major-jump upgrades: locks pin siblings (flarum 1→2, 2026-10)
- Widening root `composer.json` constraints does NOT free `composer.lock`-pinned sibling packages: a core-targeted `require flarum/core:<new-major> -W` reports 'Problem N: <bundled ext> v1.x requires core ^1.x conflicts with root require' because '*' is already satisfied by the locked old version. A 1→2 jump needs: rewrite constraints (e.g. jq-widen the first-party family), pin core `--no-update`, then a FULL `composer update` (own guard branch by old/new major from app settings).
- A root file rewritten by root (jq `> tmp && mv`) lands root-owned and breaks the next `sudo -u app composer` write ('./composer.json is not writable') — preserve ownership with `> tmp && cat tmp > file && rm tmp`, never mv.

## Composer advisory blocking vs old pinned majors (flarum 2026-10)
- Recent composer (seen at 2.10.2) refuses by default to install packages with live Packagist security advisories, so an old pinned major whose transitive dep got flagged (flarum 1.8 → league/flysystem ^1.0) can no longer be FRESH-installed despite correct sha256: 'these were not loaded, because they are affected by security advisories'. Fix for upgrade-test fixtures of the old major: seed `$install_dir/.composer/config.json` with `{"config":{"policy":{"advisories":{"block":false}}}}` chowned to the app user — AFTER remove (app remove wipes it) and just before install; do not ship the policy in the package unless upstream has no unflagged resolution path.

## Framework-level traps (PHP/Laravel/Eloquent, anonaddy dogfood 2026-10-11)
- Upstream artisan commands with `unique:` validations (e.g. addy.io `set-username-externalid`) exit 1 on idempotent re-runs — check the current value first and skip if unchanged.
- Eloquent morph columns (addy.io `aliases.aliasable_type`) need the FQCN (`App\\Models\\Username`); tinker inserts need `new Model()` + `forceFill()` + `save()` (MassAssignmentException on `create()`).
- Laravel app system user needs `adm` group membership when a scheduled command reads `/var/log/mail.log` (root:adm 0640) — add in the permissions helper or `anonaddy:parse-postfix-mail-log` fails every run with "Cannot read log file".
- Laravel session debugging ladder (when login round-trips fail): (1) prove headers reach PHP with a temp probe file logging `$_SERVER['HTTP_YNH_USER']`; (2) prove the session round-trips by decrypting the cookie's `prefix|sid` with `artisan tinker` + `app('encrypter')->decrypt(..., false)` and checking the sid key exists in redis (remember the `options.prefix` is auto-applied by phpredis connections — query WITHOUT it through the manager); (3) add a temporary `web`-middleware closure route returning `session()->all()` + `Auth::check()` to see exactly what the kernel loads. FPM opcache serves stale routes/controllers for a while after edits — `systemctl reload php8.4-fpm` after each file change before concluding anything.

## Root-helper apps: keep helper, sudoers and file lists in sync
- A helper installed to /usr/local/bin is a COPY: workspace edits to conf/apply.py are inert until redeployed (`install -m 0755 conf/apply.py $APPLY_BIN` or a full app upgrade). Stale-helper symptom: sudoers allows the new mode but the binary argparse-rejects it ("invalid choice") — redeploy the helper before debugging the webui route that calls it.
- Every new helper subcommand needs THREE sudoers updates: the heredoc in scripts/install, the heredoc in scripts/upgrade, and the live /etc/sudoers.d/<app> for same-session testing; check with `visudo -cf` after editing.
- Keep the `install -m 0644` file lists in scripts/install and scripts/upgrade IDENTICAL (webui .py, every template, static assets, runtime conf): a template present in install but missing from upgrade 500s the new route after upgrade; a file deleted from the package but still copied by upgrade leaves a stale template shadowing the new one.

## Wrapping an upstream .deb (when no YunoHost-compatible source exists)
- Pin the deb per architecture with sha256 (GitHub Release asset URLs are stable and hashable; upstream apt repos 404 whole suites — curl the repo layout before designing around one). Download → `echo "<sha>  <file>" | sha256sum --check --strict -` → `apt-get -y -o Dpkg::Options::="--force-confold" install --no-install-recommends <deb>`.
- CONFIG BEFORE DEB: a deb postinst auto-starts the service with the STOCK config, which binds upstream-default ports and collides with any same-class app already running. `mkdir -p` the config dir and `ynh_config_add` the managed config BEFORE installing the deb — the postinst start is then harmless, and dpkg keeps the pre-laid file at the conffile path under --force-confold.
- Keep the deb's NATIVE layout (unit name, /etc/<app>, /var/lib/<app>): its AppArmor profile grants file access only to those paths, so relocating breaks confinement. The package manages config + nginx + `yunohost service add <unit> --log=...` around the deb's own artifacts.
- Two same-class apps on one server: the manifest has NO port question type — ask extra ports as `string` questions whose help text names the sibling app's colliding upstream defaults, and fail fast in install with an `ss -H -ltn "( sport = :$port )"` availability check in _common.sh, before anything is provisioned.

## nginx conf for single-entry PHP apps (Laravel & friends) — linkstack 2026-10-28
- `try_files $uri $uri/ /index.php?$query_string;` UNDER `alias` breaks: the internal redirect re-resolves against the SERVER root (error log shows `open("/usr/share/nginx/htmlindex.php")`) — every pretty URL nginx-404s while `/index.php/route` works. Fix: root installs use `root` (via `#root_path_only`/`#sub_path_only` marker lines); the fallback goes to a NAMED location with an explicit `fastcgi_param SCRIPT_FILENAME <abs>/index.php;` — immune under both root and alias since the app has a single PHP entry point.
- A `php -S` scratch smoke does NOT exercise the nginx conf. Before shipping any non-trivial nginx conf, run it in a real rig (nginx -c with the rendered conf on a scratch port + the php-fpm pool, or a root-level nginx site include): request a static asset, a pretty route, and the php entry directly. Two cycles running, the arm that live-tested nginx shipped working URLs and the arm that only read the conf shipped dead ones — static reading of nginx confs has a ~100% miss rate on routing bugs.
- Restore must re-render config BEFORE any artisan/CLI bootstrap: Laravel's env-editor (routes/web.php loads it at boot) hard-dies "File .env does not Exists" if `artisan config:clear` runs first — and if the backup script never captured `.env`, only a settings-driven re-render saves the restore. Back up `.env` OR re-render it in restore before the first app command; verify by restoring into a purged state.
