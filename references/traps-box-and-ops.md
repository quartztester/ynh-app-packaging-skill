# This-box and yunohost-ops discipline (ynh-app-packaging)

Carved from platform-traps.md 2026-10-27 (router there). How to DRIVE yunohost operations safely (installs, locks, PTYs, op logs) and this server's quirks (nginx, DNS, locks). Applies when testing packages on the live box.

## Running yunohost operations (agent discipline)
- Agent-side secret auto-redaction falsifies auth gates (Hermes-class runtimes, 2026-10): the runtime silently rewrites `password=<literal>` / `-u user:pass` patterns in EXECUTED commands (not just display), so inline-curl login tests fail 401 against a perfectly good credential and files written via such commands contain `***`. Never conclude "app auth is broken" from inline login tests: pass secrets at runtime (argv `python3 - "$VAR"`, `@file` whose content never appeared literally in a command, env expansion) and byte-check (`wc -c`, `cat -A`) before believing any negative.
- Run every long yunohost op (install/upgrade/restore/backup create — minutes each) as a DETACHED background job that survives the agent's tool-call timeout and reports on completion — NEVER inside a foreground tool call or a code-exec cell. Foreground timeouts tear down the session and SIGTERM the yunohost driver, which lingers ~a minute waiting on its apt child and then dies mid-provision — leaving a half-registered app. Detach per agent: Hermes `terminal(background=true, notify=true)`; Claude Code run-in-background or tmux; other CLIs `tmux new-session -d` or `nohup … > /tmp/op.log 2>&1 &` then poll the log. Chain dependent stages into ONE background script, each stage waiting on the previous script's process (`while pgrep -f <script-name> >/dev/null; do sleep 20; done`), so the whole sequence completes unattended and reports once.
- `yunohost app install <dir> -a "k=v&k=v"` args must match manifest choices exactly (e.g. `invite_only`, not `disable_registration`) — and the args string is query-string parsed: join with `&`, NEVER commas. A comma-joined blob parses as one unknown key, the install prompts for the "missing" questions, and dies "Not a tty" even though you passed everything; commas glued into a VALUE instead surface as a misleading "Pick a valid value for <key>" form error that names the wrong argument.
- `yunohost app install` from a non-tty shell dies with "Not a tty, can't do interactive prompts" even when every manifest arg is passed via `-a` (moulinette's prompt requires os.isatty(1)). PREFERRED agent pattern: plain background job `yunohost app install <dir> -a "k=v&k=v" --force` (no wrapper) — `--force`/`-f` skips the 3rd-party-app DANGER prompt; this worked for every install/upgrade/restore in the anonaddy session. Installing on a pty WITHOUT `-f`: TWO prompts stack — the DANGER confirm (answer `Yes, I understand`) then the PRE_INSTALL notice (bare Enter), ~10–15 s apart; submit both via your agent's pty-input mechanism (Hermes: process_manage submit) or the job hangs invisibly. The `script -qec '...' /tmp/log` wrapper is a fallback but has two traps: it buffers ALL output until exit (a long background job looks hung with an empty log), and WITHOUT `-f` the DANGER prompt inside the script pty hangs forever ("terminal doesn't support cursor position requests (CPR)") until killed. `app remove` has NO force flag — use the script wrapper or a plain background job for it. `yunohost app upgrade <app> -u <dir> -F` also needs `-F`.
- Give long ops a generous timeout; if one gets killed mid-provision it can leave a stale `/var/run/moulinette_yunohost.lock` (delete before retrying) — after any timeout, check `yunohost app list` + `systemctl is-active` first: the rollback may have completed cleanly, and re-running against a half-state is what makes a mess.
- A running `yunohost backup create` holds the GLOBAL operation lock — installs queue behind it ("Another YunoHost command is running") for the backup's full duration; the nightly yuno-archive at 00:00 local runs 30-90 min. Never kill the backup; queue behind it. Identify the holder with `pgrep -af yunohost` (ignore the -api daemons) plus `ls -t /var/log/yunohost/operations/*.log | head -1` + tail.
- **A PTY background install that SUCCEEDED can still hold the global lock forever (loomio, 2026-10-27)**: the pty-wrapped `app install` printed "Installation completed" but its python never exited (hung on the pty EOF) — for 3+ hours every later `app config set` queued silently ("Another YunoHost command is running... Still waiting...", the waiter sits in hrtimer_nanosleep) while lockless commands (`config get`, `log list`) kept working, so the box looked healthy. No stale `.lock` file exists in this failure mode — the flock lives on the live process. Diagnosis: `pgrep -af "yunohost app"` for a driver older than the last operation + `ps` etime; fix: kill the holder, the lock releases instantly. After ANY pty install completes, verify the driver actually exited before starting lock-taking follow-ups.
- Op-log forensics: per-operation logs live at `/var/log/yunohost/operations/<ts>-<op>-<app>.log`; DOT-PREFIXED siblings (`.name.success`, `.name.parent.yml`) are journal-internal stream markers, NOT proof of completion. Verify by process aliveness, log line-count growth over ~15s, `systemctl is-active`, and `dpkg -l` for the debs involved.
- Late background-job notifications can surface HOURS after the fact and describe SUPERSEDED attempts — a tracked op that later failed/succeeded twice reports both outcomes out of order. Before reacting to any completion notice, `yunohost log show <log-id-from-the-notice>` and read the timestamps + failing step; a failed `app upgrade` rolls back to its safety backup, so a late exit-1 usually means nothing for current state. And any verification done while an upgrade was still running in the background RACED it — re-check version/settings/permissions after the final notification before reporting.
- `unset PYTHONPATH` before every yunohost CLI call (or the pre-upgrade safety backup dies on pydantic). Same for the agent runtime's `TMPDIR` (a private scratch dir under /root): it leaks through `sudo -E` inside `ynh_composer_exec` to composer running as the app user, which dies mid-build with 'curl error 23 … Failure writing output to destination' / 'Unable to create temporary file' — a harness artifact, not a package defect; `export TMPDIR=/tmp` before launching the op (flarum 2.0.2, 2026-10).

## Testing against the portal / SSO without collateral
- NEVER change a real YunoHost user's password to test SSO walk-in — create a dedicated test user (`yunohost user create`) instead, or verify server-side by injecting `YNH_USER` headers with curl. A password typed into a terminal command lives in the transcript: after such a test, reset the account's password back and tell the user plainly what happened.
- YunoHost portal login is scriptable: `POST /yunohost/portalapi/login` with JSON `{"credentials":"user:password"}` returns the `yunohost.portal` JWT cookie scoped `.DOMAIN` (covers app subdomains) — use it with `curl -b` + `--resolve` to test ssowat-injected flows end-to-end without a browser.

## This server's quirks
- **nginx -t is GLOBAL: one broken conf anywhere kills every later reload** (loomio restore, 2026-10-27): a hand-managed `/etc/nginx/conf.d/<other-domain>.conf` referencing a not-yet-issued cert made `nginx -t` fail box-wide, so an app restore died at its final `ynh_systemctl nginx reload` with only "Job for nginx.service failed" in the op log. When an operation fails at the reload step, run `nginx -t` FIRST — the culprit is usually an unrelated conf. Corollary: concurrent admin sessions on one box can deadlock via the global yunohost lock (session A's backup holds it while session B's cert job waits) AND via nginx validity (B's broken conf blocks A's restore); unblocking often means completing the other session's missing prerequisite (e.g. `yunohost domain add <domain>` to materialize the expected cert) rather than touching their files.
- Hand-managed confs for a domain that later becomes a yunohost domain: `domain add` regen-conf will not clobber the unmanaged top-level `<domain>.conf` (kept as manually-modified), but the clean layout is per-domain fragments in `conf.d/<domain>.d/`.
- nginx `location ~` regexes containing `{n}` quantifiers MUST be quoted (`location ~ "^/[0-9a-f]{10}/x$" {`): unquoted, nginx tokenizes the brace as the block opener → `[emerg] unknown directive "10}/..."` and the reload fails mid-install (the failed install's rollback may mask it). Pre-validate a rendered fragment with an isolated mini conf (`pid/events/http/server{ include fragment }`) + `nginx -t -c`, never against the live tree.
- Local dnsmasq resolves the server's own domains to `::1` + `127.0.0.1`; box has no IPv6 listener → self-hairpin requests to the public URL hang on ::1. Test local vhosts via `curl --resolve host:443:127.0.0.1` or Host header.
- nginx nchan crashloops after repeated reloads (memstore assertion, multiple master processes, nothing accepts connections): `systemctl stop nginx; pkill -9 nginx; systemctl start nginx`.

## Bash/script traps found in lifecycle testing (anonaddy_ynh, 2026-10-11)
- `sed "s@^PATTERN=$@..."` — `$@` inside double quotes expands to positional parameters and corrupts the sed script ("unterminated s command"). Quote the pattern: `sed 's@^PATTERN=$@'"REPL"'@'`.
- `ynh_mysql_db_shell` output includes the column header row — `| tail -n1` before parsing.
- Extra manifest permissions (beyond `main`) default to `allowed: nobody` — set `<perm>.allowed = ["all_users"]` in the manifest (plausible_ynh pattern) or a gated sub-permission blocks everyone.
- **Scripted local-dir installs need `--force` (qbittorrent benchmark 2026-10-27)**: YNH core unconditionally stamps any local-directory install `quality = thirdparty` (app_utils.py, no catalog lookup), which triggers a HARD confirm ("Yes, I understand") that a non-tty CLI cannot answer — "ERROR Not a tty, can't do interactive prompts". `yunohost app install <dir> -a ... --force` bypasses it. API/webadmin installs skip the confirm entirely.
- **A CLI death mid-install can leave a half-registered app (qbittorrent benchmark 2026-10-27)**: the timeout-killed install triggered YNH's rollback (deps + service removed) yet the app stayed in `app list` with a live service on the first failure. Cleanup recipe: `yunohost app remove <id>` (works on half-installs), then verify unit/nginx-conf/user/ports are actually gone before reinstalling; the data dir persists by design (`remove` vs `purge`).
- **A FAILED install's rollback prints "Deprovisioning data_dir" but does NOT delete it** (same data-safety design): `--force` retries inherit the prior attempt's files, so an empty-dir init contract dies "folder appears to already have files in it" while the same invocation passes in scratch on a truly empty dir. Between failed gate retries, `rm -rf` the data dir yourself; packages for empty-dir-init apps should pre-clean or fail loudly on a dirty data dir.
- Operator-kernel env trap (2026-10-27): a Python kernel whose PATH puts a venv `python3` first breaks `yunohost` CLI (`#!/usr/bin/env python3` → ModuleNotFoundError). Run yunohost from a clean `env -i HOME=/root PATH=/usr/sbin:/usr/bin:/sbin:/bin` context, or from the plain shell session.

## Helpers 2.1 / arg-serialization traps (qbittorrent_static, 2026-10-28)
- `ynh_exec_warn_less` and `ynh_wait_tcp_port` DO NOT exist in helpers 2.1 (they v1-isms); verify any helper with `grep -h "^ynh_" /usr/share/yunohost/helpers.v2.1.d/*` before use, or the install dies mid-script on `command not found`. Same for `ynh_print_log` — 2.1 only has `ynh_print_info`/`ynh_print_warn`/`ynh_script_progression`; a missing helper inside a success branch killed an otherwise-complete install via `set -e` rollback.
- `yunohost app install -a` wants `&`-delimited `KEY=VALUE` pairs (`domain=x&path=/`); space-separated silently misparses (domain arg rejected as invalid) and JSON is not accepted.
- Boolean manifest questions can arrive as `1`/`0` (not `true`/`false`) depending on arg path — normalize with a case statement before comparing in conf rendering, or a true-flag branch silently never fires (this left DHT/PeX enabled in an I2P-only "anonymous" config).
- **Apps that rewrite their own conf at shutdown (qBittorrent, anything Qt-QSettings): render-while-running gets clobbered.** The lifecycle order must be stop → render → start; a `restart` after re-render lets the shutdown write stomp the fresh file (and it will also stomp manual `sed` edits made while running).
- Rendering helpers outside a lifecycle script (manual re-render): export `YNH_HELPERS_VERSION=2.1` before sourcing `/usr/share/yunohost/helpers` (dispatcher defaults to v1 and `ynh_config_add` is "not found"), and export settings as env vars yourself; `yunohost app shell` is interactive-only.
- Non-catalog apps cannot be upgraded in-place (`No apps can be upgraded`) — doc re-apply recipes must use `yunohost app upgrade <id> -u <repo-url>`.
- qBittorrent 5.x `WebUI\LocalHostAuth` semantics are inverted vs intuition: `false` = loopback connections SKIP auth (webapplication.cpp isAuthNeeded); `true` demands auth everywhere. Read the enforcement site, not the key name.
