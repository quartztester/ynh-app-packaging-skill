# Install questions, config panels, admin docs — the YNH-rendered GUIs (UX doctrine)

Both GUIs the webadmin shows are DECLARATIVE, rendered by YunoHost core from the package: `manifest.toml [install.*]` → the install form; `config_panel.toml` → the postinstall panel. Nothing "transfers to YunoHost" — scripts just receive answers as env vars. Mechanics/traps: traps-helpers-and-panels.md (panels), ssowat-integration.md (permissions). This file is the WHAT-to-expose + wording doctrine, calibrated 2026-10-28 against 199 catalog level-8 apps in five rounds (round 1: nextcloud, roundcube, jellyfin, syncthing, searxng, rustdesk-server, stirling-pdf, forgejo, joplin; round 2: archivebox, libretranslate, peertube, mastodon, etherpad, freshrss, paperless-ngx, homeassistant, uptime-kuma, bookstack; rounds 3–5: 180 more, category-stratified, incl. gitea, adguardhome, bonfire, calibreweb, n8n, cryptpad, moodle, gotosocial, loops, hedgedoc — scripts, round selections and per-round stats in `research/` in this repo).

## Install questions — ask almost nothing
- STANDARD TYPES CARRY THEIR OWN GUI TEXT: `domain`/`path`/`user`/`group` questions render core-provided labels + help. Level-8 apps ship them ask-less (96/99 domains, 90/99 init_main_permission have EMPTY ask; the exceptions are headless sidecars like gitlab-runner that ask neither domain nor permission). Write `ask`/`help` ONLY for app-specific semantics a stock label can't express (corpus precedents: nextcloud `user_home`, forgejo `init_admin_permission`).
- Budget: corpus median 3 questions (mode 3; 59% of round-5's 100 apps ask ≤3), range 0–10 — gemserv/opensearch ship ZERO install questions, rustdesk-server ONE, and over half the corpus (58% round-5) ships NO path (full-domain only). The upper end is genuine bootstrap: loops 10 and bonfire 8 (ActivityPub instance identity + invite + federation), calibreweb/concrete5 7 (CMS content + own auth) — question count scales with what the app genuinely can't default. A question is justified only when a non-technical admin must choose it at install AND it can't be a safe panel toggle later.
- Core set, in order: `domain` → `path` (only if the app truly works under a subpath) → `init_main_permission` (group; default = the app's real visibility) → `admin`/`init_admin_permission` ONLY when the app has its own auth AND SSO is impossible (auth-backend-integration.md; password questions = documented local last resort) → `language` only if upstream ships real translations (select, curated choices). Extra permissions (API/admin surfaces) get their own ask-less `init_<name>_permission` group questions (archivebox/paperless pattern). Corpus-validated: every password-asking app in round 4 (11/11) declares `sso != true` — zero violations; password questions appear exactly where SSO is impossible, and only ~14% of level-8 apps can SSO at all.
- Visibility is a PERMISSION, not a boolean: fold "is this public?" into `init_main_permission` (group type, default = the app's real visibility); extra booleans only for app-internal behavior beyond URI gating (nextcloud `user_home` precedent). The corpus default is `visitors` — public-by-default in 96% (87/91 round-5); `admins` only for inherently-private data (2/91). The legacy `is_public` boolean is dead: 1/30 round-3 (fediverse semantics, misnamed), 0/50 round-4, 0/100 round-5.
- Custom questions: bilingual ask (en+fr), short question phrasing; help = the consequence of the answer; ALWAYS a default — every optional in the corpus carries one (5/5 round 4), the sole no-default shape is genuinely-optional FREE TEXT where empty is meaningful (instance description, third-party API keys — bonfire pattern); select over free string when choices enumerate; prefer privacy-safe defaults (bonfire `invite_only` defaults true). Custom questions are RARE in level-8 apps (~0.5 per app).
- NEVER ask: ports, DB names, internal paths, SMTP details (panel later), API keys (panel later), anything derivable (full URL from domain+path), anything with a safe default changeable later. Long legacy forms converge on this too: the old ArchiveBox form (path + is_public boolean + more) is TODAY 5 ask-less questions with visibility folded into `init_main_permission`.

## Config panel — what a non-technical self-hoster actually flips
- Sections by CONCERN with short names (forgejo: Registration / Repository / Email / Privacy / Federation), not by config-file layout. Panels are OPTIONAL in practice — only ~14–22% of corpus apps ship one — and the typical panel is 1–3 options (dumbdrop pin, conduit registration toggles, collabora msfonts); nextcloud 5-section and forgejo 12-section × ~29 are the corpus POLES, not the norm. NEVER expose the app's whole config surface — the ecosystem itself trims toward this (LibreTranslate's old 15-knob rate-limit wall is 18 options today, and the remaining tuning-ish ones sit in one `[main.specific]` section).
- ask = plain question ("Disable registrations?"); help = consequence ("Disallow registration, only allow admins to create accounts."). The panel's help text IS that option's documentation — ADMIN.md must not repeat it.
- Types: boolean + `yes = "true"` / `no = "false"`; number for counts; select for enums; tags for lists; `type = "button"` for ACTIONS (repair/regen — nextcloud permissions button); `visible` JS for dependent options; `bind = "settings"` unless the value lives elsewhere (getter env-poisoning trap: traps-helpers-and-panels.md). Adoption is generational: newer panels (libretranslate, paperless-ngx) bind EVERY option, while long-lived lineage (gitea, forgejo, nextcloud) still carries custom get__/set__ — bind is the pattern to write today. Pair it with the section-level `services = ["__APP__"]` key so core restarts the app after apply (13/22 round-5 panels; officially documented) — custom restart code inside set__ functions is the legacy substitute.
- EXCLUDE: numeric tuning walls (rate-limit/char-limit knobs — advanced limits live in the app's config file, pointed to once from ADMIN.md), internal paths/ports/DB credentials, anything the app's own admin UI already exposes BETTER (never mirror the app's full settings page).
- Every panel value round-trips through settings + app state + service (gate: quality-gates.md §3) and survives upgrade unchanged (never rewrite user-chosen values — listmonk cycle proof).
- Mail panel fields (server/port/ssl/from/user/pwd) + From-domain trap: postfix-integration.md §Outbound.

## ADMIN.md / README — task pointers, not encyclopedias
- README.md is BOT-GENERATED — the catalog's `apps_tools/readme_generator` rewrites it ("shall NOT be edited by hand") from the manifest `description.en` + upstream links; don't hand-maintain, and its absence is the one tolerated linter warning. In catalog practice 0/80 round-3/4 apps ship DESCRIPTION.md, only ~2% README_fr, ~24% POST_INSTALL.md, ~6% PRE_INSTALL.md (risk-gated) — the example_ynh full file set is this skill's bar, deliberately above catalog practice.
- ADMIN.md corpus reality: most apps cluster at 4–24 lines (round-4 median 4.5, p75 14.5; peertube 1, audiobookshelf 4, searxng 7, jellyfin 20) with a RISK-CORRELATED long tail to ~124 (adguardhome 124 explaining port-53 exposure + DNS-amplification risk, bonfire 114, domoticz 98, gitea 86). Length scales with the infra-risk of the exposed options, not with app size: a DNS-exposing toggle earns an amplification warning (and a PRE_INSTALL.md note at decision time); a normal web app earns ~10 lines. The model is searxng: install dir, where custom settings live (and why not to edit the defaults), one upgrade-behavior caveat. Headings are TASKS (forgejo: User synchronization / Notes on SSH usage / Private Mode / Uploaded files size), never system diagrams.
- A line earns its place ONLY if it needs shell/app-side action a panel can't do. NO: panel-option restatement, packager internals (patch mechanics, DB provisioning, helper choices — those live in the repo where maintainers look), implementation notes an admin can't act on, facts stated twice.
- Worked trim example: Loomio's ADMIN.md 68 → ~40 lines keeping services+log locations, mail verify commands, backup/restore timing; cutting patch/PG-extension internals, the duplicated no-LDAP note, and hand-edit warnings the panel makes moot.
- DESCRIPTION.md = the readme_generator's blurb input, 1–2 user-facing sentences (manifest `description.en/fr` mirrors it — that's what the catalog actually reads); catalog presentation rules: repo-hygiene.md.
