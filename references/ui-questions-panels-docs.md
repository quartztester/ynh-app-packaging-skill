# Install questions, config panels, admin docs — the YNH-rendered GUIs (UX doctrine)

Both GUIs the webadmin shows are DECLARATIVE, rendered by YunoHost core from the package: `manifest.toml [install.*]` → the install form; `config_panel.toml` → the postinstall panel. Nothing "transfers to YunoHost" — scripts just receive answers as env vars. Mechanics/traps: traps-helpers-and-panels.md (panels), ssowat-integration.md (permissions). This file is the WHAT-to-expose + wording doctrine, calibrated 2026-10-28 against 49 catalog level-8 apps in three rounds (round 1: nextcloud, roundcube, jellyfin, syncthing, searxng, rustdesk-server, stirling-pdf, forgejo, joplin; round 2: archivebox, libretranslate, peertube, mastodon, etherpad, freshrss, paperless-ngx, homeassistant, uptime-kuma, bookstack; round 3: 30 more, category-stratified, incl. gitea, adguardhome, bonfire, bookwyrm, audiobookshelf, cinny, baikal, biboumi, ampache, gitlab-runner — stats preserved in the packaging workspace `ui-research/`).

## Install questions — ask almost nothing
- STANDARD TYPES CARRY THEIR OWN GUI TEXT: `domain`/`path`/`user`/`group` questions render core-provided labels + help. Level-8 apps ship them ask-less (48/49 domains, 45/49 init_main_permission have EMPTY ask; the exceptions are headless sidecars like gitlab-runner that ask neither domain nor permission). Write `ask`/`help` ONLY for app-specific semantics a stock label can't express (corpus precedents: nextcloud `user_home`, forgejo `init_admin_permission`).
- Budget: corpus median 3–4.5 questions, range 1–8; rustdesk-server ships ONE (`[install.domain]` alone), and 43% of round-3 apps ship NO path at all (full-domain only — peertube, homeassistant, uptime-kuma, gitea-class). The 8-question corpus max is ActivityPub instance bootstrap (bonfire: instance name + description + invite-only + media size + optional API keys) — question count scales with what the app genuinely can't default. A question is justified only when a non-technical admin must choose it at install AND it can't be a safe panel toggle later.
- Core set, in order: `domain` → `path` (only if the app truly works under a subpath) → `init_main_permission` (group; default = the app's real visibility) → `admin`/`init_admin_permission` ONLY when the app has its own auth AND SSO is impossible (auth-backend-integration.md; password questions = documented local last resort only — catalog reality is looser, 7/10 own-auth apps in round 2 still ask admin+password, but this skill's bar is SSO-first) → `language` only if upstream ships real translations (select, curated choices). Extra permissions (API/admin surfaces) get their own ask-less `init_<name>_permission` group questions (archivebox/paperless pattern).
- Visibility is a PERMISSION, not a boolean: fold "is this public?" into `init_main_permission`'s default (visitors vs admins); extra booleans only for app-internal behavior beyond URI gating (nextcloud `user_home` precedent). Scale check: an `is_public`-named boolean survives in only 1/30 round-3 apps — and even there it means fediverse visibility (app-internal semantics), just misnamed.
- Custom questions: bilingual ask (en+fr), short question phrasing; help = the consequence of the answer; ALWAYS a default — the sole catalog exception is genuinely-optional FREE TEXT where empty is meaningful (instance description, third-party API keys — bonfire pattern); select over free string when choices enumerate; prefer privacy-safe defaults (bonfire `invite_only` defaults true). Custom questions are RARE in level-8 apps (~0.4 per app in round 3).
- NEVER ask: ports, DB names, internal paths, SMTP details (panel later), API keys (panel later), anything derivable (full URL from domain+path), anything with a safe default changeable later. Long legacy forms converge on this too: the old ArchiveBox form (path + is_public boolean + more) is TODAY 5 ask-less questions with visibility folded into `init_main_permission`.

## Config panel — what a non-technical self-hoster actually flips
- Sections by CONCERN with short names (forgejo: Registration / Repository / Email / Privacy / Federation), not by config-file layout. Both corpus poles are level 8: nextcloud 5 sections × 1 option; forgejo 12 × ~29. NEVER expose the app's whole config surface — the ecosystem itself trims toward this (LibreTranslate's old 15-knob rate-limit wall is 18 options today, and the remaining tuning-ish ones sit in one `[main.specific]` section).
- ask = plain question ("Disable registrations?"); help = consequence ("Disallow registration, only allow admins to create accounts."). The panel's help text IS that option's documentation — ADMIN.md must not repeat it.
- Types: boolean + `yes = "true"` / `no = "false"`; number for counts; select for enums; tags for lists; `type = "button"` for ACTIONS (repair/regen — nextcloud permissions button); `visible` JS for dependent options; `bind = "settings"` unless the value lives elsewhere (getter env-poisoning trap: traps-helpers-and-panels.md). Adoption is generational: newer panels (libretranslate, paperless-ngx) bind EVERY option, while long-lived lineage (gitea, forgejo, nextcloud) still carries custom get__/set__ — bind is the pattern to write today.
- EXCLUDE: numeric tuning walls (rate-limit/char-limit knobs — advanced limits live in the app's config file, pointed to once from ADMIN.md), internal paths/ports/DB credentials, anything the app's own admin UI already exposes BETTER (never mirror the app's full settings page).
- Every panel value round-trips through settings + app state + service (gate: quality-gates.md §3) and survives upgrade unchanged (never rewrite user-chosen values — listmonk cycle proof).
- Mail panel fields (server/port/ssl/from/user/pwd) + From-domain trap: postfix-integration.md §Outbound.

## ADMIN.md / README — task pointers, not encyclopedias
- README.md is BOT-GENERATED — the catalog's `apps_tools/readme_generator` rewrites it ("shall NOT be edited by hand") from the manifest `description.en` + upstream links; don't hand-maintain, and its absence is the one tolerated linter warning. In catalog practice 0/30 round-3 apps ship DESCRIPTION.md — the manifest description IS the working blurb source; ship DESCRIPTION.md anyway per the example_ynh file set (readme_generator's preferred input).
- ADMIN.md corpus reality: most apps cluster at 4–24 lines (median ~10; peertube 1, audiobookshelf 4, searxng 7, jellyfin 20) with a RISK-CORRELATED long tail to ~124 (adguardhome 124 explaining port-53 exposure + DNS-amplification risk, bonfire 114, domoticz 98, gitea 86). Length scales with the infra-risk of the exposed options, not with app size: a DNS-exposing toggle earns an amplification warning (and a PRE_INSTALL.md note at decision time); a normal web app earns ~10 lines. The model is searxng: install dir, where custom settings live (and why not to edit the defaults), one upgrade-behavior caveat. Headings are TASKS (forgejo: User synchronization / Notes on SSH usage / Private Mode / Uploaded files size), never system diagrams.
- A line earns its place ONLY if it needs shell/app-side action a panel can't do. NO: panel-option restatement, packager internals (patch mechanics, DB provisioning, helper choices — those live in the repo where maintainers look), implementation notes an admin can't act on, facts stated twice.
- Worked trim example: Loomio's ADMIN.md 68 → ~40 lines keeping services+log locations, mail verify commands, backup/restore timing; cutting patch/PG-extension internals, the duplicated no-LDAP note, and hand-edit warnings the panel makes moot.
- DESCRIPTION.md = the readme_generator's blurb input, 1–2 user-facing sentences (manifest `description.en/fr` mirrors it — that's what the catalog actually reads); catalog presentation rules: repo-hygiene.md.
